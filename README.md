# dirtree

`dirtree` is a terminal directory-tree browser: progressive-disclosure navigation in the browser overlay, a background-indexed quick open finder, an in-browser incremental jump-to-file typing mode, a background content-search mode, a syntax-highlighted file preview pane, and live refresh as files change on disk, all in a single dependency-free binary.

The spec was derived from a working Python/curses prototype (iterated on directly in a terminal, feature by feature, against real usage) and generalized so it can be reimplemented in any language, with no assumption of a particular runtime. The implementation here is Go, using `tcell` for terminal rendering — see "Language and Dependencies" in `CLAUDE.md` for the rationale.

## Goals

- **Single static binary, no required runtime dependencies.** No interpreter, no package manager, no dynamically-loaded libraries needed at runtime. Optional-but-desired features (syntax highlighting, `.gitignore` parsing) may use a statically-linked library compiled into the binary (e.g. syntax highlighting uses `chroma`), but must never depend on something present only on the target system at runtime.
- **Cross-platform terminal UI** that behaves correctly inside terminal multiplexers (Zellij, tmux) that don't always deliver resize signals reliably.
- **Usable as a released artifact** other projects can pull in by version (e.g. a container image build fetching a pinned release binary), not something that only lives copy-pasted inside one repo.

## Installation

**macOS or Linux, via Homebrew:**

```
brew install nitti/tap/dirtree
```

This installs from the [`nitti/homebrew-tap`](https://github.com/nitti/homebrew-tap) tap, which is kept up to date automatically on every tagged release.

**Direct download:** grab a prebuilt binary (`darwin`/`linux`, `amd64`/`arm64`) from the [releases page](https://github.com/nitti/dirtree/releases), extract it, and put `dirtree` on your `PATH`.

**From source:** see "Build and run" below.

## Contents

- [`specs/SPEC.md`](specs/SPEC.md) — full behavioral specification: CLI, data model, traversal/ignore rules, navigation, background indexing, quick open and jump to file, preview pane, layout, rendering conventions, keybindings, resize handling.
- [`specs/TESTING.md`](specs/TESTING.md) — acceptance criteria, expressed as test cases the implementation must satisfy.
- [`docs/GO_STYLE.md`](docs/GO_STYLE.md) — Go-specific style and architecture rules (layering, error conventions, concurrency, tooling), enforced via `.golangci.yml` and `make lint`.
- [`docs/ANIMATION_IDEAS.md`](docs/ANIMATION_IDEAS.md) — brainstormed, not-yet-decided animation ideas, checked against the animation principles in `specs/SPEC.md` §5.3.
- `cmd/dirtree/` — CLI entry point (argument parsing, path resolution, startup error handling, `--version`).
- `internal/tree/` — the lazily-loaded node model, flattening, navigation semantics, jump-to-file's visible-row matching (`JumpMatches`), and the refresh/merge logic behind live updates (spec §3.1, §3.4, §4.3, §6.1).
- `internal/ignore/` — the dependency-free `.gitignore`/`.dirtreeignore` pattern subset (spec §3.2).
- `internal/index/` — the background full-tree index used by quick open and content search, including live rebuilds (spec §4.1, §6.1).
- `internal/match/` — quick open's substring/glob query-matching rule and jump to file's simpler leaf-name prefix rule (spec §4.1, §4.3).
- `internal/search/` — the background content-search scan: case-insensitive substring matching against each indexed file's (byte-capped, binary-excluded) content, cancelable mid-scan when a newer query supersedes it (spec §9).
- `internal/preview/` — file reading (`Load`, distinguishing a failed open from a successful one per spec §2.2), best-effort syntax highlighting, and line wrapping for the preview pane (spec §2.1).
- `internal/find/` — in-file find: case-insensitive substring matching over an already-open file's lines, in rune coordinates that compose with `internal/preview`'s wrapped display rows (spec §2.4).
- `internal/openfiles/` — the open-files list: per-entry scroll/goto/in-file-find state, open/reuse/fail semantics, the list-overlay's remove/reorder operations, and the dropdown overlay's paging/bulk-reorder math (spec §2.2, §2.3, §2.4).
- `internal/spinner/` — the delayed-loading-indicator timing/frame logic, including the minimum-display-duration skip and the full badge decision sequence (spec §5.2).
- `internal/toast/` — the "show in full, then fade left-to-right from an anchor point" timing primitive (spec §5.3) `internal/spinner`'s completion message builds on.
- `internal/watch/` — the `fsnotify`-backed, debounced filesystem-change watcher driving live refresh (spec §6.1); OS-facility-adjacent like `internal/ui`, verified manually.
- `internal/ui/` — the tcell-backed terminal-rendering layer (draw loop, input handling, resize polling, wiring the watcher to tree/index refresh). Not unit-tested; verified manually in a real terminal (see Status below).
- `.goreleaser.yaml` / `.github/workflows/release.yml` — cross-compiles and publishes a GitHub Release plus an updated Homebrew cask on every `vX.Y.Z` tag push.

## Build and run

```
make build          # builds ./dirtree
make run             # builds and runs against .
make run ARGS=/path  # builds and runs against a specific path
make test            # runs the unit test suite
make lint            # runs golangci-lint (see docs/GO_STYLE.md)
```

Or directly with `go`:

```
go build -o dirtree ./cmd/dirtree
./dirtree [path]
```

## Releasing

Push a tag matching `vX.Y.Z` to trigger the release workflow:

```
git tag v0.1.0
git push origin v0.1.0
```

This cross-compiles `darwin`/`linux` × `amd64`/`arm64` binaries, attaches them (plus checksums) to a GitHub Release, and pushes an updated cask formula to `nitti/homebrew-tap`. Requires the `HOMEBREW_TAP_GITHUB_TOKEN` repository secret (a PAT scoped to `contents: write` on the tap repo only).

## Status

The implementation matches `specs/SPEC.md`'s open-files-primary-view design: a running list of open file previews as the primary view, with the browser (§3), an open-files switcher (§2.3), and quick open plus jump to file (§4) as overlays reachable from it (§5.1 covers the resulting view model). This was rebuilt in seven stages (each landed as its own PR) from an earlier design where the browser was the primary screen, followed by a keybinding/terminology pass that split the original combined jump/fuzzy-picker overlay into the two single-purpose overlays described below and renamed "tree explorer" to "browser" throughout the spec, tests, and code:

1. Core open-files data layer: `internal/openfiles` (open/reuse/fail semantics, remove/reorder), `preview.Load`'s failed-vs-opened result type, and `spinner`'s minimum-display-duration-skip/badge-decision logic.
2. Browser overlay wiring: auto-opens on startup, full §3.4 navigation, Space/`a` open files through `internal/openfiles` with inline failure messaging, per §2.2.
3. Jump/fuzzy-picker overlay wiring from both entry points (superseded — see stage 8): reveal-in-tree and open-into-list, with the header legend and Enter/Space mapping flipping per entry point.
4. Open-files list overlay (`Tab`): list rendering, Enter/`x`/Shift-Up/Shift-Down/Escape (§2.3).
5. Primary preview view: real content rendering (gutter, syntax highlighting, wrapping), scrolling, goto-line, and per-entry state restoration (§2.1).
6. Browser's dual split/popup layout (§5.1), recomputed every frame: split view puts the browser pane on the left with a read-only preview pane on the right; popup view floats a bordered window over the unmodified, full-width preview.
7. System behaviors and a full manual verification pass (resize polling, escape timeout, live filesystem refresh, the spinner badge's full sequence including debug mode, open-failure messaging for binary/permission-denied files).
8. Split stage 3's combined jump/fuzzy-picker overlay into two single-purpose overlays per current `specs/SPEC.md` §4: **quick open** (`O`, toggle, reachable from the primary preview view, opens the selected match into the open-files list) and **jump to file** (`/`, reachable only from within the browser, reveals the selected match in the browser and replaces the browser view while active). `B` (browser) and `O` (quick open) are now both toggles — pressing the same key again closes the overlay it opened, the same as Escape.

The pure-logic layers (`internal/tree`, `internal/ignore`, `internal/index`, `internal/match`, `internal/preview`, `internal/openfiles`, `internal/spinner`, `internal/search`) have automated test coverage against every group in `specs/TESTING.md`. `internal/ui` is hand-verified in a real terminal (tmux): startup (originally the auto-opened browser, now the empty preview view — see the startup fix noted further below); navigation, expand/collapse; Space/`a` open actions including inline binary/permission-denied failure messages; `B`/`Tab`/`O`/`/`/Escape/`q` view switching, including `B` and `O` closing their own overlay as a toggle; quick open's single open action and jump to file's single reveal-in-browser action (including jump to file replacing and then correctly returning to the browser); the open-files overlay including Shift-Up/Shift-Down reordering; real preview rendering with scrolling, goto-line, and per-entry scroll-state restoration; live filesystem refresh (add/delete reflected in both the browser and the background index) while the app is running; and the spinner badge's full threshold/spinner/completion/fade sequence, confirmed both in normal builds (tiny directories correctly show nothing at all) and via `-tags spinnerdebug` (bypasses only the perceptibility threshold; the minimum-display-duration floor, completion message, and fade still run on their normal schedule). The periodic resize-poll ticker's behavior inside Zellij — the primary target multiplexer per `specs/SPEC.md` §6.2, which doesn't always deliver resize signals reliably — has also been confirmed working as expected in earlier stages and was not re-verified in stage 8 (the resize/ticker code itself is unchanged by the rename).

**Content search (spec §9)**, added after the stages above: a separate `s`-triggered overlay, reachable from both the browser and the primary preview view, that scans indexed files' content (not just paths) for a case-insensitive match — a plain substring by default, or a regular expression in regex mode (Ctrl+R toggles it; an invalid pattern shows an inline error instead of scanning) — running the scan in a cancelable background goroutine per keystroke/mode-toggle so typing never blocks on a large tree, with a threshold-suppressed animated spinner (mirroring the indexing badge) once a scan runs long enough to be worth showing. The query lives on its own row beneath the header, with a background distinct from the results list so it's unmistakable at a glance. Results render as a two-level, expandable list — one row per matching file (all expanded by default) disclosing every matching line within it, not just the first — with Left/Right to collapse/expand a file's hits, Return to open the selected row and jump straight to its line (leaving the overlay open, so several hits can be opened in a row), and Ctrl+U to clear the query. Unlike the other overlays, neither Return nor Escape discards content search's state: opening a result doesn't close the overlay, and Escape (which does close it) leaves the query, results, mode, selection, and disclosure state exactly as they were, reset only when the user explicitly clears or changes the query. `internal/search`'s matching (both modes)/binary-detection/cancellation logic is unit-tested; the overlay wiring itself (both entry points, live query typing including literal spaces, regex-mode toggling and error display, disclosure toggling, jump-to-line accuracy, Escape-preserves-state, the slow-scan spinner, and the index badge rendering in this overlay too) is hand-verified in a real terminal alongside the rest of `internal/ui`.

**Post-stage fixes**: the browser and quick open toggle keys were corrected from `B`/`O` to lowercase `b`/`o` (a typo relative to `specs/SPEC.md`'s intent of single-character, non-shifted keybindings); the browser's Space and `a` open actions were collapsed into a single open action that always opens a file into the primary preview without closing the browser (`a`'s "open, keep open" behavior is now the only behavior, since closing on open turned out to not be worth keeping), and that action's key was subsequently moved from Space to Return; the top menu bar now always shows the tree root path (abbreviated with `~` for the home directory), left-aligned, rather than the full path of whatever file happens to be open, with the keybinding legend right-aligned — dropping the root path first if the terminal is too narrow to fit both — and the open file's own root-relative path is shown in a separate title bar directly above the preview content; every overlay's header now left-aligns its own content (query, label, or root path) against a right-aligned keybinding legend the same way; Escape no longer quits from the primary preview view (only `q` does), to avoid an accidental Escape discarding the session's open-files state; every keybinding legend/header now labels the confirm key `Return` rather than `Enter`, matching the physical key on a Mac keyboard; and quick open's `o`/Escape "toggle" was found to break ordinary typing (any filter query containing the letter "o" — a common one — closed the overlay instead of filtering), so quick open no longer treats `o` as a close key once open, leaving Escape as the only way to close it (the browser's `b` toggle is unaffected, since the browser isn't a text-entry surface); and quick open is now also reachable with `o` from within the browser overlay (previously primary-preview-only), replacing the browser view the same way jump to file and content search already do — Escape returns to the browser if that's where it was opened from, while successfully opening a match always lands on the primary preview view regardless of entry point, mirroring content search's existing entry-point handling; and file-specific actions (currently just goto-line, `g`) moved out of the global header/title bar's legend and into the file title bar's own right-aligned legend, shown only where the preview is actually interactive (omitted, path-only, in the split-view browser's read-only preview pane) — the global bar is now app-wide-actions-only, and new file-specific actions belong in the file title bar going forward.

**In-file find (spec §2.4)**, added after the fixes above: a `less`-style `/`-triggered search within the currently-displayed file's own content, distinct from quick open/jump to file (which match paths, never content) and content search (which matches content across the whole tree, not one open file). The prompt and live status (query, current/total match count, and a "wrapped to top/bottom" note) live in the file title bar rather than a separate row, per the file-specific-actions convention above; every match is highlighted in the preview itself (the current match distinguished from the rest), and `n`/`N` step between matches with wraparound. Find state is tracked per open-files entry, independent across files, the same way scroll/goto-line already are. Escape, initially inert here as everywhere else at the primary view, was given one narrow exception: it clears an active find (otherwise there was no way to dismiss the highlighting/status short of running a new search) — it's still not a general "back out" key and still never quits.

**Rendering fixes**, found while investigating "mangled" previews: (1) `internal/preview.Highlight`'s token-to-line attribution had a bug where a chroma token whose value spanned a newline (a whitespace token covering "end this line, then indent the next one," e.g. `"\n    "`) attributed the text *after* the newline to the line that had just ended, since the line index was only advanced after the whole token was processed rather than at the newline itself — this silently dropped a line's leading indentation and shifted everything after it, most visibly on YAML files (heavily indentation-dependent, and chroma's YAML lexer produces exactly this token shape constantly); fixed by advancing the line index as each newline is encountered mid-token, interleaved with flushing the surrounding text to the correct (old-or-new) line. (2) Raw tab characters were never expanded — they reached the terminal as a single narrow column instead of the width a terminal normally gives them — visibly breaking alignment on any tab-indented file (Go source among them, being gofmt'd); fixed by expanding tabs to 8-column tab stops once at read time, before highlighting/wrapping/guttering/find ever see the text, so none of them need their own tab-width handling. Both are unit-tested: a regression test reconstructs every highlighted line's text from its segments and compares it to the source line, and a tab-expansion test covers both a mid-line tab and tab stops resetting per line. `internal/find`'s matching logic is unit-tested; the overlay-free wiring itself (prompt open/typing/cancel/execute, `n`/`N` stepping and wrap notes, scroll-to-match, and highlighting including in the split-view browser's read-only preview pane) is hand-verified in a real terminal alongside the rest of `internal/ui`.

**Copy mode (spec §2.1)**, added after a report that mouse-selecting preview text also grabbed the line-number gutter: a `c`-toggled display preference that strips the gutter and syntax-highlighting color from the preview, leaving a screen with nothing on it but the file's own characters at full pane width — color was never actually a selection risk (tcell applies it via terminal escape sequences outside the text stream, not literal codes a selection could copy), but the gutter genuinely was. In-file find's match highlighting stays visible in copy mode regardless, since it's not selectable text either and remains useful while locating what to copy. It's tracked per open-files entry rather than globally (initially built global, then moved per-entry once it became clear a copy-mode preference for one file has nothing to do with the next file you switch to — the same reasoning behind scroll/goto-line/find already being per-entry), so it applies wherever that entry's preview is drawn, including the split-view browser layout's read-only pane; the file title bar renders in a visually distinct style and tags its content `[copy mode]` whenever the displayed entry is in copy mode, regardless of which of the row's other states (idle, active find, find prompt) is otherwise showing, so it's always legible rather than only appearing in the idle case. Hand-verified in a real terminal alongside the rest of `internal/ui`.

**Word-wrapping**, replacing the original fixed-column wrap: `wrapLineSegments` now only breaks mid-word as a last resort (a word that doesn't fit within a full-width row even on its own) — otherwise it breaks at the end of a run of spaces (dropping them, the standard word-wrap convention) or immediately after a dash/hyphen (keeping it, since the dash is itself the visual break marker). Unit-tested for the space-preferred case, moving a word whole to the next row rather than splitting it, dash breaks, the mid-word hard-break fallback, and triggering-space-dropped-vs-real-trailing-space-preserved.

Word-wrapping briefly led copy mode astray: reasoning that a multi-row mouse selection across wrapped continuation rows copies a line break the file doesn't actually have, copy mode was changed to disable wrapping entirely and clip a long line at the pane's edge instead. That traded a cosmetic problem for a functional one — anything past the clipped edge was never drawn at all, so it couldn't be selected by any means, making it impossible to copy an entire long line rather than just occasionally picking up an extra line break in a multi-row selection. Reverted: copy mode wraps exactly like normal display (gutter/color are still stripped), so every character of every line stays visible and selectable somewhere on screen, accepting the wrap-induced-line-break limitation as inherent to any fixed-width terminal grid rather than something worth losing content over.

**Jump to file reworked from a fuzzy finder into an in-browser incremental jump (spec §4.3)**: it no longer opens a full-screen flat-list overlay searching the entire background-indexed tree — that behavior now belongs solely to quick open. Jump to file is instead a typing mode layered directly on the still-visible browser: candidates are exactly the browser's current flattened row list (whatever the tree's live expand/collapse state already exposes, so it never itself expands or collapses anything on the user's behalf), matched by case-insensitive prefix against each row's own leaf name rather than its full path. Typing live-moves the browser's own selection to the first match; Tab/Shift-Tab (or Down/Up) cycle among several matches in display order; Return simply leaves jump mode with the selection wherever it landed; Escape restores the exact selection/scroll from before `/` was pressed. Because jump to file no longer expands ancestor directories to reveal a match, `tree.RevealPath` (and its "resolution failure" case) became dead code and was removed along with its tests. The new candidate/matching logic is pure and unit-tested (`match.PrefixMatches`, `tree.JumpMatches`); the mode's key handling and live-highlighting are wired in `internal/ui` and hand-verified in a real terminal alongside the rest of that layer.

**Open-files list overlay redesign (spec §2.3)**: the overlay no longer fully replaces the screen — it now renders as a small dropdown-style popup over the (unmodified) primary preview view, the same "floating window over an unchanged background" idiom the browser's popup layout already used, just without that layout's split-view alternative (the open-files overlay is always a popup). It shows at most 10 entries at a time ("a page"), each row labeled with its 0-9 position on that page so a digit key jumps straight to and opens that entry, closing the overlay immediately — a faster path that coexists with the existing arrow-keys-then-Return flow rather than replacing it. Page Up/Page Down turn a full page at a time (clamped at the first/last page, not wrapping, mirroring the file preview's own Page Up/Down semantics); Shift-Page-Up/Shift-Page-Down do the equivalent bulk move for reordering, since walking an entry across several pages one Shift-Up at a time was impractical. Which page is showing, and each row's on-page digit, are derived from the selected index every frame (`internal/openfiles.Page`/`PageBounds`) rather than stored and kept in sync — so removals and reorders re-flow the visible numbering for free. The popup's border carries a "▲"/"▼" at the top/bottom when an adjacent page exists, and a counter ("11–20 of 23") plus keybinding legend renders inside the box. The pure paging/bulk-reorder math (`Page`, `PageCount`, `PageBounds`, `SelectPage`, `SelectDigit`, `List.MoveUpPage`/`MoveDownPage`) is unit-tested in `internal/openfiles`; the dropdown's rendering itself is hand-verified in a real terminal alongside the rest of `internal/ui`.

**Browse, quick open, and content search made mutually exclusive (spec §5.1)**: `o` (quick open) and `s` (content search) had each been reachable both from the primary preview view and from within the browser overlay (and, for content search, from within either), replacing the browser view in place while remembering it as the "return to" screen on Escape. That made it possible to chain from one file-selection mode directly into another without ever passing back through the primary preview view, which made it easy to lose track of which mode's in-progress state (a browser selection, a quick open query, a search) was about to be abandoned. All three are now reachable only from the primary preview view: `o` and `s` are no-ops from within the browser overlay, `s` is a no-op from within quick open, and `o` is a no-op from within content search — Escape from quick open or content search always lands back on the primary preview view rather than on whichever overlay it happened to be entered from. This removed the `quickOpenEntryPoint`/`searchEntryPoint` tracking entirely, along with the browser's now-dead `o`/`s` key handling; the browser's own header legend was updated to stop advertising them. The open-files list overlay (`Tab`) is unaffected — it isn't one of the three file-selection modes and remains reachable only from the primary preview view as before.

**Header/title bar mode labels**: the header/title bar's left side now shows a bold, all-caps mode label (`BROWSE`, `QUICK OPEN`, `SEARCH`/`SEARCH (REGEX)`, `JUMP`) in place of the tree root path whenever a mode other than the primary preview view is active, similar to how modal editors like `hx` always surface the current mode — only the label itself is bold, the legend sharing the row stays normal weight. Jump to file's query, which previously appeared directly in the header (`/query`), moved to its own input row directly below the header instead, the same convention quick open and content search already use for their own queries — user-entered text no longer appears in a row now reserved for the mode label.

**Quick open and content search reveal the opened path in the browser (spec §4.2, §9.2)**: opening a file from either overlay now expands every intermediate ancestor directory and moves the browser's selection to it, so pressing `b` afterward shows where that file lives without further navigation, rather than leaving the browser wherever it last was. This resurrects `tree.RevealPath`, removed earlier when jump to file was reworked into an in-browser incremental jump that deliberately never expands anything on the user's behalf (see above) — that reasoning doesn't apply to quick open/content search, since both search the whole tree regardless of current disclosure state and have no other way to reflect what they just opened.

**Browser overlay's split-view/popup dual layout removed (spec §5.1, issue #35)**: a bug surfaced where jump-to-file's query input row was drawn at full terminal width instead of the browser pane's own width, bleeding into the read-only preview pane in split view. Investigating it raised a bigger question: the split-view preview pane was never a live preview of the browser's selection — it just kept showing whichever file had last been opened, static, until Return opened something new — so weighed against that narrow benefit, the dual layout's ongoing cost (a whole extra layout algorithm, two separate draw paths sharing screen real estate differently, and a recurring class of pane-boundary bugs like this one) wasn't worth it. The browser overlay now always renders full-screen at every terminal width, the same shape as quick open: a header row plus the flat row list filling the rest of the screen. This removed `internal/layout` entirely, `computeSplitLayout`/`browserPaneWidth` from `internal/ui/app.go`, and `drawBrowserSplitView`/`drawBrowserPopup` from `internal/ui/render.go` (folded into a single `drawBrowserOverlay`). Hand-verified in a real terminal: the browser and jump-to-file render full-width at both narrow and wide terminal sizes, the jump query row no longer bleeds past its own content, and live resize no longer flips between two layouts (there's only one now).

**Toast primitive extracted, then a unified red error flash added for any failed operation on a row (spec §5.3, §2.2, §6.1)**: the bottom-right badge's completion-message fade math moved out of `internal/spinner` into a new `internal/toast` package (`Decide`), a standalone "show in full, then fade left-to-right from an anchor point" primitive; `spinner.BadgeDecision` now calls it directly, with no behavior change. A live-refresh discovering that an already-loaded directory newly lost read permission was first surfaced as a toast built on that same primitive, then reconsidered: an error is diagnostic text the user may be reading, and a toast that fades out on its own schedule risks disappearing mid-read. Redesigned into a brief red flash on the affected row instead (`styleFlashError`, the same brief-attention mechanism as the existing green post-open flash) with the failure message appended inline on that row — the flash decays, the inline text does not, staying until overwritten by a later success. That treatment then generalized to cover every open-failure in the app, not just directory-listing errors: a file that fails to open (permission denied, binary) from the browser, quick open, or content search now gets the exact same red flash + inline message on its own row, replacing the previous separate bottom-status-line messages (`browserMessage`/`finderMessage`/`searchMessage`, now removed) those three used before. The browser reuses `tree.Node.Err` directly (the same field a directory-listing failure already sets); quick open and content search track the failed path/message separately (`finderErrorPath`/`searchErrorPath` et al.) since their rows are rebuilt from the index/search results every keystroke rather than being stable node identities — cleared whenever the query changes. A clipboard-copy confirmation toast was considered (`docs/ANIMATION_IDEAS.md`) but deliberately not built: there's no clipboard-copy action in dirtree to confirm yet. `internal/toast` and `tree.RefreshTree`'s newly-erroring reporting are unit-tested; the flash/inline-message rendering across all three overlays is hand-verified in a real terminal alongside the rest of `internal/ui`.

Three refinements followed: (1) a directory failing to load when the user directly expands it (Right-arrow) now gets the same red flash the live-refresh case already had — previously only a live-refresh-detected failure flashed; an expand-triggered one showed the inline error but no flash. (2) Every open-failure message (`tree.errText`/`preview.errText`) now strips the path Go's `*fs.PathError` normally repeats (e.g. "open /a/b: permission denied" becomes just "permission denied") — redundant once the message is already shown inline on that path's own row. (3) `tree.Node.LoadChildren` previously marked a directory "loaded" even when the read failed, so a failed load's error lingered forever — collapsing and re-expanding it (or pressing Right again) silently no-opped instead of retrying, even after the underlying problem (e.g. permissions) was fixed. It now only skips a retry once a load has *succeeded*, so fixing the problem and re-expanding actually clears the error rather than requiring a live-refresh to happen to notice on its own.

**Live reload of open files (spec §6.1a)**: an open file's preview content used to only ever reflect whatever was on disk at the moment it was opened — editing it in another program while dirtree had it open left the preview silently stale until the user closed and reopened it. Since every open file necessarily lives in a directory that's already loaded, and therefore already watched (§6.1), no new watch plumbing was needed: `openfiles.List.Reload` now runs on every debounced live-refresh, comparing each open entry's on-disk mtime against the mtime recorded at its last (re)load, re-reading and re-highlighting only the ones that actually changed — for every open entry, not just the currently-displayed one, so a background file is never stale by the time the user switches to it. A reload mutates the existing entry in place (same identity, same list position, same displayed status) and invalidates its line-wrap cache and any in-file find state, since both are derived from content that just changed; scroll position is left alone rather than snapped back to the top, so it self-clamps naturally the next time the entry is scrolled or displayed. A file that's deleted or becomes unreadable between checks is left with its last-known content rather than being reloaded or cleared, matching §6.1's existing deleted-file handling. This is the first real caller of the generic toast primitive introduced above (previously only used internally by the indexing badge): a successful reload surfaces a bottom-right toast naming the reloaded file(s), reusing `drawCornerBadge`'s anchor/fade — unlike the directory-error case above, this is routine confirmation rather than diagnostic text, so letting it fade on its own schedule is the right call here. `openfiles.List.Reload` is unit-tested (changed-vs-unchanged mtime, multiple open files, entry-identity/list-order/displayed-index preservation, the deleted/unreadable case, and wrap-cache/find-state invalidation); the toast rendering and end-to-end live-reload behavior are hand-verified in a real terminal alongside the rest of `internal/ui`.

**Minimum terminal size (spec §6.4)**: below 40 columns or 10 rows, none of the app's layouts (header + legend, popups, split content) can render without truncating or overlapping in misleading ways, so `draw` now checks the terminal's current dimensions first, every frame, and — if either is below the minimum — replaces the entire frame with a dedicated too-small screen instead of whatever view/overlay was active. Rather than a block of text, it draws the single undersized dimension as red arrows pointing apart with the required size centered between them (`← 40 →` on the vertical-center row for width, a vertical `↑`/`10`/`↓` stack for height), addressing individual cells directly rather than through any row-width helper so it stays legible even far below its own minimum; when both dimensions are short, only one indicator is shown at a time (whichever is proportionally further below its own minimum, ties favoring width) rather than trying to fit both into a space too small for either. Key input is suppressed for the duration (checked in the main loop before dispatching to `handleKey`), so nothing typed while it's showing can change app state; resizing back above both thresholds simply resumes drawing whatever was already there, untouched. Hand-verified in a real terminal: resizing narrower than 40 columns, shorter than 10 rows, and both at once (confirming the proportionally-worse dimension's indicator is the one shown, including a tied case favoring width) from each of the primary preview view and every overlay; resizing back restores the exact prior view; and the too-small screen itself doesn't crash when resized far below its own minimum (down to a handful of columns/rows).

**Legend consistency, ordering, and narrow-terminal hierarchy (spec §5.2, §7)**: every keybinding legend in the app now follows one convention — primary action, then secondary/navigation actions, then destructive/clear actions, then escape/cancel/close last — and each entry carries a drop priority for narrow terminals, replacing the old binary "drop the left-hand label, then hard-clip the legend text" behavior. `internal/ui.legendFit` tries the full legend alongside the left-hand content (root path, mode label, file path) first, then the full legend alone, then drops whole priority-3 entries, then whole priority-2 entries — never reordering survivors or truncating an entry mid-text. Several real, already-working keybindings that had no legend entry anywhere were filled in: jump to file's Shift-Tab/Up previous-match and `/` slash-to-expand, quick open's and content search's Tab/Shift-Tab row navigation, the open-files list's Enter-to-open, and the goto-line prompt (which previously had no legend at all). `legendFit`'s tiered fit/drop logic is unit-tested in `internal/ui`; the visual result of resizing through each tier's drop points is hand-verified in a real terminal alongside the rest of that layer.

**`b` is no longer a toggle on the browser overlay (spec §5.1, §7)**: pressing `b` while the browser is already open used to close it, mirroring quick open's short-lived `o`-as-close-key behavior (removed above for the same reason). Escape is now the sole key that closes any overlay, browser included — `b` inside the browser overlay is simply a no-op, matching the rest of the app's overlays. This mainly removes a footgun for jump-to-file queries starting with `b`, since jump mode already intercepted `b` before it could reach the toggle, and keeps "how do I close this" a single consistent answer across every overlay.

**Content search's regex-mode indicator moved off the header (spec §9.2)**: the header's mode label used to switch between `SEARCH` and `SEARCH (REGEX)` depending on Ctrl+R's toggle state, which competed with the keybinding legend for the header row's width and disappeared entirely once a narrow terminal dropped the mode label. The indicator now lives on the query-input row instead, prefixing the prompt (`[regex] > needle` vs. plain `> needle`) — that row never competes with the legend for space and is never dropped, so the indicator stays visible at any terminal width. The header's mode label is now always the plain `SEARCH`, matching `BROWSE`/`QUICK OPEN`/`JUMP`'s single-state labels.

**Startup no longer auto-opens the browser (spec §1, §5.1)**: the app now starts on the primary preview view's empty state with no overlay active, superseding stage 2's original "browser auto-opens on startup" behavior described above — pressing `b` opens the browser same as always. The open-files list overlay auto-opening the browser when its last entry is removed (§2.3) is unchanged, since that's a separate, still-live behavior. Along with this, several other small UX fixes landed together: the browser's own legend now advertises left/right expand/collapse (previously a real, working keybinding with no legend entry); content search's hit rows are now indented further than their owning file row's own path text, so they read as visually nested rather than lining up with it; Tab/Shift-Tab were dropped from quick open and content search (both already had Up/Down for the same navigation, making the second binding low-value) — jump to file's own Tab/Shift-Tab is unaffected; and jump to file's header/title bar mode label no longer switches to a distinct `JUMP` label while active, staying `BROWSE` throughout (only the legend and query row change), its query-row prompt changed from `/query` to `> query` to match quick open/content search's own prompt convention, and slash-to-expand no longer clears the query row back to blank with no trace of what was typed — each committed path segment now accumulates in a disclosed-path prefix shown ahead of the live query (e.g. `> internal/ui/`) instead.

## Non-negotiable constraints

- **No required runtime dependencies.**
- **No assumed language or runtime** — `specs/SPEC.md` is phrased in terms of observable behavior, not any particular language's types or library calls.
- **Terminal resize must be handled by polling**, not solely by relying on a resize signal/event — see "Resize handling" in `specs/SPEC.md`.
