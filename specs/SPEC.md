# dirtree — behavioral specification

This document specifies observable behavior only. Any data structure, module split, or algorithm name below is a *description of behavior*, not an implementation mandate — implement it however is idiomatic in the chosen language, as long as the described behavior holds.

The sections below are ordered to mirror the app itself: start at the primary view (§2), then each way of getting a new file into it — the browser (§3) and quick open / jump to file (§4) — then how it's all laid out and rendered on screen (§5), then the ambient system behaviors that apply everywhere (§6), and finally the keybindings recap (§7).

## 1. CLI

```
dirtree [path]
```

- `path` is optional, positional, defaults to `.` (the process's current working directory).
- The path is resolved to an absolute path at startup.
- If the resolved path is not a directory, exit immediately with a non-zero status and a one-line error to stderr (e.g. `dirtree: not a directory: <path>`). Do not enter the terminal UI.
- On successful startup, the primary view is the file preview (§2.1), initially empty (no files open) — see §5.1 for the full view model.
- No other flags are required for behavioral parity with the prototype. Additional flags (e.g. `--version`, `--help`) are at the implementer's discretion but must not change default behavior.

## 2. Primary view: file preview and open-files list

This is the screen the app centers on: a single file preview, backed by an ordered list of every file the user has opened during the session. §2.1 covers the mechanics of rendering one file's content; §2.2 covers the list that holds multiple open files and how opening/displaying/closing one works; §2.3 covers the overlay used to switch between them.

### 2.1 File preview

Each entry in the open-files list (§2.2) has its own preview content and its own scroll/goto-line state, computed and tracked independently — the mechanics below apply per open file, not globally.

- **Reading**: a small capped peek (1,000,000 bytes in the prototype — pick something in that neighborhood) from the start of the file determines, synchronously and fast, whether the open itself fails: a read failure (permission denied, path no longer exists, etc.) or binary-ness (a NUL byte in that peek, §2.2's checks) both short-circuit the open before an entry is ever created, exactly as before. Once that check passes, the entry's actual content is read and (for a highlighted-tier entry, below) highlighted in the background, not synchronously as part of the open call — an already-open entry's content is never re-read on every display, same as before, but a newly-opened entry now appears immediately and lights up once its background pass reports progress (§5.2's "building…" indicator) rather than blocking input while it loads.
  - **Two tiers, decided from the file's size** (`internal/preview.HighlightCeiling`, a tunable default of 25MB — a `var`, not a hard requirement of that exact number, in the same spirit as the byte cap above): a file at or under the ceiling is fully read, decoded, and highlighted in the background exactly as described in the rest of this section, then kept fully resident while it's one of the most-recently-displayed few open files (`internal/openfiles.ResidentCap`, below). A file over the ceiling gets no highlighting at all (every segment renders as plain text) and is never held fully resident: only the lines needed for the current viewport (plus a scroll margin) are read on demand, seeking directly into the file via the line-offset index below, so memory use for an arbitrarily large file stays proportional to the viewport rather than the file. The tier is decided at open time and **re-decided the same way on every reload** (§6.1a) rather than treated as sticky for the entry's lifetime: a file that grows past the ceiling between reloads is demoted to the plain-text tier (so it stops being fully read/highlighted in the background, the same memory bound a freshly-opened file that size would get), and one that shrinks back under it is symmetrically promoted back to the highlighted tier. A tier change resets the entry's scroll position to the top, since a display-row index means something different under each tier's model (below) and doesn't carry over meaningfully.
  - **Resident-content eviction for the highlighted tier** (`internal/openfiles.ResidentCap`, a small fixed count — 4 by default): the open-files list has no cap on how many files can be open at once, but only the `ResidentCap` most-recently-*displayed* highlighted-tier entries keep their fully decoded/highlighted content resident at any moment — displaying an entry beyond that count evicts the least-recently-displayed one's content (never the currently-displayed entry itself, and never a plain-text-tier entry, which is never held fully resident anyway per above) rather than leaving every highlighted-tier file ever opened in the session resident until manually closed. Eviction is invisible to everything except memory use and, potentially, timing: an evicted entry's other state (scroll position, wrap cache, find state, tier, copy mode) is untouched, and its content is transparently rebuilt — re-read and re-highlighted in the background, the same as a freshly-opened file — the next time it's displayed, showing the same "building preview…" placeholder a new open shows until that finishes. Ordinary quick switching among a handful of recently-viewed files finds their content still resident and pays no extra cost; switching back to a file that fell out of the resident set pays the same latency its original open did.
  - **Content availability before the background pass finishes**: for either tier, the preview content area shows a "building preview…" placeholder in place of the gutter/rows until the entry's background pass (below) has finished — for the highlighted tier this is normally too brief to ever be seen, but for the plain-text tier over a very large file it can be a real, visible wait. This is a deliberate simplification of the more ambitious "show plain-text content immediately once its offset is known, even before the whole pass finishes" behavior a fuller design would aim for: gating on the same single "done" signal goto-line already gates on (below) keeps the implementation's mental model simple ("ready or not"), at the cost of an otherwise-avoidable wait on a very large plain-text file specifically. Scrolling, goto-line, copy mode, and in-file find (§2.4) are otherwise unaffected once the pass finishes.
  - Decode as UTF-8, replacing invalid sequences rather than failing, and split into lines. If the file's actual size exceeds the byte cap, append a line noting the content was truncated at that many bytes.
  - **Tab expansion**: each line's tab characters are expanded to spaces up to the next tab-stop column (8 columns in the prototype, tab stops resetting at the start of every line), so a tab-indented file (a Go source file, for instance) renders with the same visual alignment a terminal would normally give it, rather than each tab occupying a single narrow column — this expansion happens once at read time, so highlighting, wrapping, line-number gutter alignment, and in-file find's column coordinates (§2.4) all operate on the already-expanded text with no separate tab-width bookkeeping of their own.
  - An empty result set becomes a single empty line (so the preview always has at least one row to render).
- **Syntax highlighting** (best-effort, must not require a *runtime* dependency — a statically-linked library compiled into the binary is fine, per the Language and Dependencies section of `CLAUDE.md`):
  - Attempt to categorize each line's text into a small fixed set of display categories: `comment`, `string`, `number`, `keyword`, `function`, `operator`, falling back to `text` for anything uncategorized (identifiers, punctuation, whitespace, and — for prose/markup lexers whose native token vocabulary doesn't map onto this code-oriented set — headings/emphasis/link text, which are folded onto the nearest existing category rather than left unhighlighted).
  - Language detection is by file extension/basename (and/or a shebang-line sniff for extensionless scripts), covering whatever languages the underlying lexer implementation supports; there is no requirement to match a general tokenizer's exact token boundaries, only to produce a reasonable, stable per-line categorization. A hand-written per-language rule table is one acceptable implementation; a vendored general-purpose lexer library (e.g. Go's `chroma`) mapped down onto the fixed category set above is another.
  - If no lexer/rule-set matches the file, or highlighting fails for any reason, fall back to rendering the whole file as plain `text` — never let a highlighting failure block the preview from showing.
  - Highlighting produces, per source line, an ordered list of `(text_fragment, category)` segments that concatenate back to the original line.
- **Line wrapping**: each source line's segments are word-wrapped to fit a target display width (in columns): a row only ever breaks in the middle of a word as a last resort, when the word doesn't fit within a full-width row even on its own — otherwise the break lands at the end of a run of spaces (those triggering spaces are dropped entirely rather than reappearing as leading whitespace on the next row — real trailing whitespace at a line's actual end is unaffected, only a wrap-induced break drops anything) or immediately after a dash/hyphen (kept on the row it ends, since the dash itself is the visual break marker, same as hyphenated prose). No wrapped row ever exceeds the width. Wrapping must be recomputed whenever the available width changes (e.g. terminal resize); copy mode (below) wraps the same way. Each wrapped row remembers which source line it came from; only a source line's *first* wrapped row carries that line's number (continuation rows are unnumbered), so the gutter (§5.2) only prints a number once per source line.
- **Line-number gutter**: reserve a fixed-width column (wide enough for the largest line number in the file) plus a short separator, printed to the left of content on every row; continuation rows print blank space in the number column instead of repeating or incrementing. For a plain-text-tier entry, there's no exact total line count until its background pass finishes — render against the best current lower bound instead, floored at a minimum width of 4 digits regardless of how few lines have been seen so far (most files end up past 1,000 lines eventually, so this floor means the large majority never visibly resize their gutter at all; only a file that ends up past 9,999 lines still shows a grow-then-snap once the pass completes).
- **Copy mode** (`c` key, toggle, SPEC.md §7): strips the line-number gutter entirely (content occupies the full pane width instead) and renders every line in plain text, without syntax-highlighting color, so a terminal mouse selection dragged across the preview grabs nothing but the file's own characters — no gutter digits mixed in, and (though this was never actually a risk, since tcell applies color via terminal escape sequences outside the text stream, not literal codes a selection could copy) no ambiguity about it either. Copy mode still word-wraps exactly like normal display (above) — an earlier version instead disabled wrapping and clipped a line at the pane's edge, on the theory that wrapping's extra screen rows could pick up a line break a multi-row selection wouldn't otherwise have; that traded a cosmetic problem for a worse one, since anything past the clipped edge was never drawn at all and so could not be selected by any means regardless of technique. Word-wrapping keeps every character of a line visible and selectable somewhere on screen, which matters more than a multi-row selection occasionally picking up an extra line break at a wrap point — an inherent limitation of any fixed-width terminal grid that copy mode does not attempt to fully solve. In-file find's match highlighting (§2.4) remains visible in copy mode — it isn't literal selectable text any more than syntax color is, and staying visible is more useful than not. Copy mode is tracked per open-files entry (§2.2), independent across files like scroll/goto-line/find state above — switching to a different open file does not carry the setting over, and switching back restores whatever it was left at for that file. It applies wherever that entry's preview is drawn, including underneath the open-files-list overlay's read-only view (§2.3). The file title bar (§5.2) renders in a visually distinct style while the displayed entry is in copy mode, and its content is tagged `[copy mode]` regardless of which of the file title bar's other states (idle, active find, find prompt) is otherwise showing, so its on/off state for the current file is always legible, not just from the legend text.
- **Scrolling**: Up/Down scroll by one display row; Page Up/Page Down scroll by one viewport height; scrolling is clamped so it never goes negative or past the point where the last display row would leave the viewport. Scroll position is stored per open-files entry (§2.2) and restored exactly when switching back to that entry. **Exception for the plain-text tier** above: since that tier only ever holds a windowed slice of the file rather than a whole-file wrap cache, Up/Down and Page Up/Page Down instead move by that same count of *source lines* rather than display rows — a deliberate, flagged simplification of the scroll model for that tier only, still clamped so it never goes negative or past the last known line.
- **Goto-line** (`g` key): prompt for a numeric line number at the bottom of the preview area, alongside a short keybinding legend (§5.2's fit/drop rule applies to this row too) documenting Return/Ctrl+U/Escape below; Return jumps the current entry's scroll position to that source line's first display row (clamped to `[1, total source lines]`); Escape cancels the prompt without changing scroll; only digit, backspace, and Ctrl+U (clear the entire input, §7) input is accepted while the prompt is open.
- **Background pass**: every opened entry starts a single background pass (`internal/preview.StreamIndex`) that streams the file once, recording the byte offset of every line's start regardless of tier, and — for a highlighted-tier entry — also decoding, tab-expanding, and highlighting its full content into memory, per the two-tier split above. This pass is what the "building preview…" placeholder and the file title bar's "building…" legend spinner (§5.2) both reflect, and what the plain-text tier's windowed reads (above) seek through once it's done. While it's running, pressing `g` does not open the goto-line prompt: it instead briefly flashes the file title bar red and shows an inline "still indexing, try again shortly" message (the same red-flash-plus-inline-message convention §2.2/§5.2 uses for a failed file open), and the file title bar's legend (§5.2) replaces `[g] goto line` with a "building…" spinner once the pass has been running long enough to be perceptible (§5.3's threshold/minimum-display-duration discipline). Once the pass finishes, `g` behaves exactly as described above. A reload (§6.1a) restarts this pass for the reloaded entry.
- **Empty state**: when the open-files list has no entries (fresh startup, or the last entry was just closed), the preview view renders a short explanatory message (e.g. hinting at `b` to browse or `o` to quick-open) instead of gutter/content rows, and none of the scrolling/goto-line keys apply.

### 2.2 Open files list

The open-files list is the primary state the rest of the UI operates on: an ordered collection of files the user has opened during this session, plus which one (if any) is currently displayed in the primary preview view (§2.1).

- **Ordering**: insertion order by default, but user-rearrangable — see the open-files list overlay's (§2.3) reorder keys. A newly-opened file (one whose resolved absolute path is not already in the list) is appended to the end regardless of any manual reordering already done. Opening a file whose resolved absolute path already matches an existing entry does not create a duplicate or change that entry's position — see "open semantics" below.
- **Per-entry state**: absolute path, loaded preview content (§2.1's read/highlight results, loaded once at open time), and independent scroll/goto-line state (§2.1). Exactly one entry, or none, is the "displayed" entry at any time.
- **Open semantics** (used by §3.4's Return and §4.2's quick open): given a path,
  - if an entry for that resolved absolute path already exists in the list, do not read the file again or move the entry — just mark it as the displayed entry, preserving its existing scroll/goto state. (A file that failed to open never has an entry, per the next bullets, so any existing entry is by construction previously-successful and safe to display as-is.)
  - otherwise, attempt to read up to the byte cap (§2.1) from the start of the file:
    - if the read itself fails (permission denied, the path no longer exists, or any other OS-level read error), the open is a **failed result** carrying a short explanatory message (e.g. "permission denied," the underlying OS error text with any repeated path prefix stripped — see below) — do not create an entry, do not change the currently-displayed entry (if any), and return that result to the caller instead of a displayable file.
    - otherwise, if the read bytes contain a NUL byte, the file is binary — also a **failed result**, carrying the message "binary file, preview not available," with the same "no entry created" handling as above.
    - See "Open-failure signaling" below for what each caller does with a failed result.
  - otherwise (read succeeded and the content is not binary), continue reading/highlighting the file (§2.1), append a new entry at the end of the list with scroll reset to the top, and mark it as the displayed entry. This is an **opened result**.
- **Displaying** an entry (making it the one shown in the primary preview view) never changes list order.
- **Open-failure signaling**: an open call's result is one of "opened" (an entry now exists and is displayed) or "failed," carrying a short explanatory message — a read error and a binary file are both failed results, distinguished only by their message text; there is no separate binary-specific code path from here on. Every caller handles a failed result the same way, unified with §6.1's newly-unreadable-directory treatment as one mechanism ("the last operation attempted on this row failed"): staying exactly where it was, appending the message inline on the specific row that failed (not a separate status line), and briefly flashing that row's background red (§5.3) — the flash decays, the inline message does not, persisting until overwritten by a later successful open of that same path. The open-files list and primary preview view are untouched in this case, since no entry was created:
  - From the browser overlay (§3.4's Return): the browser does **not** close and selection does not move; the failed path's row (a `tree.Node`, so this reuses the exact same field/rendering a directory listing error already uses) shows the message inline and flashes red.
  - From the quick open overlay (§4.2) or content search (§9.2): the overlay does **not** exit and selection does not move; the failed match's row shows the message inline and flashes red the same way, tracked by path rather than a stable node identity since these rows are rebuilt from the index/search results on every keystroke — a content-search hit row's failure attributes to its parent file row, the same as its on-open flash does.
  - The message is advisory only and does not block further input — the user can immediately navigate elsewhere or attempt to open a different file.
  - A later query/scan change (quick open/content search) clears any previously-recorded failure for that context, since a new query can't say anything about a stale failure from a previous one.
  - The message omits the path: the OS's own error text for a failed open (e.g. Go's `*PathError`) repeats the path being opened (e.g. "open /a/b/c: permission denied"), but the path is already visible via the row the message is displayed inline on, so only the underlying reason ("permission denied") is shown.

### 2.3 Open-files list overlay

Triggered by `Tab` from the primary preview view (including the empty state). Unlike the other three overlays, this one does not take over the screen: it renders as a small dropdown-style popup over the (unmodified, last-rendered) primary preview view, always, regardless of terminal width. While active:

- **Paging**: the list is shown 10 entries at a time (a "page"), in list order, each rendered as its root-relative, slash-delimited path (same path-rendering convention as quick open, §4.2), prefixed with a single digit (its 0-9 position within the *current page*, not a position in the whole list) and with the currently-displayed entry (if any) marked distinctly. Which page is showing is derived from the selected index (`selected / 10`), not stored as separate state, so it never needs separate upkeep as the list is reordered or shrinks — it's simply recomputed from current state every time it's needed, the same way the rest of the app's layout is recomputed every frame from current terminal/model state rather than cached (§6.2's resize-handling discipline, applied here to list state instead of terminal dimensions).
- **Indicating more pages exist**: the popup's header area shows a range counter (e.g. "11–20 of 23") alongside the keybinding legend; a small "▲" is rendered in the box's top border when a previous page exists, and a "▼" in the bottom border when a next page exists — placed at the edge of the box each one refers to, so the affordance costs no extra content row. The legend itself lists the page-turning keys (below) only when there's more than one page — the same "don't advertise a key that does nothing right now" rule the file title bar's legend already follows (§5.2).
- A `selected` index into the whole list (not just the current page), with wraparound cycling on Up/Down (same wrap semantics as §3.4) — crossing a page boundary this way turns the page automatically, so Up/Down still walks the entire list one entry at a time, it just does so across 10-row pages instead of one continuous unpaged list.
- **Page Up / Page Down**: jump a full page forward/backward, landing on the target page's first entry (position 0). Clamped at the first/last page rather than wrapping — Page Up on the first page and Page Down on the last page are both no-ops. This mirrors the file preview's own Page Up/Down semantics (§2.1: "scroll by one viewport height," here "turn by one page") rather than introducing new vocabulary.
- **Digit keys `0`-`9`**: select-and-open in one step — if the pressed digit has an entry at that position on the current page, mark it as the displayed entry and close the overlay immediately, exactly as Return does for whatever is currently highlighted (below). A digit with no corresponding row on the current page (e.g. pressing `7` on a 3-entry final page) is a no-op. This is a separate, faster path alongside Up/Down-plus-Return — arrow-key navigation still only *moves the highlight* and still requires Return to commit, so the two methods coexist without conflict.
- **Return**: mark the selected entry as displayed, then close the overlay, returning to the primary preview view showing it.
- **`x`**: remove the selected entry from the list.
  - If the removed entry was not the displayed entry, the displayed entry is unaffected; only the list itself shrinks, and overlay selection is clamped to the nearest remaining index (preferring the entry that was next after the removed one, falling back to the new last entry if the removed entry was last). Because paging/numbering is derived from the list's current state rather than cached, the remaining entries' on-page digits and page membership re-flow immediately to reflect the shrunken list — nothing needs explicit renumbering.
  - If the removed entry *was* the displayed entry, the displayed entry becomes the adjacent surviving entry (the one after it in list order, or the one before it if the removed entry was last); overlay selection follows the same entry.
  - If the list becomes empty as a result, there is no displayed entry; closing the overlay (or its own auto-close, see below) lands on the primary preview view's empty state (§2.1) — the same state startup shows before anything has ever been opened, with no overlay auto-opened on top of it.
  - The overlay itself stays open after an `x` removal (it does not auto-close), so multiple entries can be removed in a row; it only auto-closes if the removal just emptied the list entirely, per the previous bullet.
- **Shift-Up / Shift-Down**: move the selected entry one position toward the top/bottom of the list, swapping it with its current neighbor; overlay selection follows the moved entry so repeated presses keep walking it further, turning the page automatically if the move crosses a page boundary (same page-follow behavior as Up/Down above). Unlike Up/Down's navigation wraparound, reordering does **not** wrap — Shift-Up on the first entry and Shift-Down on the last entry are both no-ops. This only changes list order (§2.2); it does not change which entry is displayed, and does not affect any entry's stored scroll/goto state. The reordered position persists for the rest of the session (until the entry is removed or the app exits) exactly like an insertion-order position would.
- **Shift-Page-Up / Shift-Page-Down**: a bulk version of the above — move the selected entry up to a full page's worth of positions (10) toward the top/bottom in one keypress, equivalent to repeating Shift-Up/Shift-Down 10 times. Like the single-step version this does not wrap: if fewer than 10 positions remain before hitting an end of the list, the entry moves as far as it can and stops there rather than being a no-op or wrapping around. This exists because one-at-a-time reordering across many pages is impractical (holding Shift-Up dozens of times to move an entry from page 4 to page 1) without needing a whole separate "jump to page N" mechanism.
- **Escape**: close the overlay and return to the primary preview view unchanged — whatever was displayed before opening the overlay is still displayed (removals already performed via `x`, if any, are not undone; only the "make this one displayed" action of Return/digit-select is what Escape skips).
- **Opening the overlay**: `selected` starts on the currently-displayed entry (or 0 if none is displayed), so the popup opens showing the page that entry is on rather than always resetting to page 1 — landing on "where you are," consistent with how switching feels centered on current state elsewhere in the app.
- If the list is empty when the overlay is opened (e.g. a fresh, file-less session's empty state, reached at startup or by escaping back to it), render an explanatory "no open files" message instead of a list, and only Escape is meaningful.

### 2.4 In-file find

Triggered by `/` from the primary preview view (§2.1), a no-op if there's no displayed entry (the empty state has nothing to search). This is a `less`-style search within the currently-displayed file's own content — distinct from quick open (§4.2, which matches *paths*, never reads a file's content), jump to file (§4.3, which matches leaf names of currently-visible browser rows, likewise never reading content), and content search (§9, which matches content but across every file in the tree, not within one already-open file). Find state — query, matches, which one is current, and the wrap note below — is tracked per open-files entry (§2.2), independently of any other open file, the same way scroll and goto-line state already are; switching to a different entry and back preserves it exactly.

- **Prompt**: `/` opens a query prompt in the file title bar (§5.2) — not the goto-line prompt's bottom row, since this is itself a file-specific action per that section's convention. Any printable character is accepted (unlike goto-line's digits-only prompt), Backspace removes the last character, Ctrl+U clears the entire input (§7), Escape cancels the prompt without changing the entry's existing find state (if any), and Return executes the search:
  - Every case-insensitive substring match of the query is located across the entry's lines, in source order (line, then column within the line).
  - The match at or after the source line currently at the top of the viewport becomes the current match ("search forward from here," the same convention `less` uses); if none exists at or after that point, the current match wraps to the very first match in the file and the wrap note (below) is set.
  - The view scrolls just enough to bring the current match into view (only if it isn't already visible, the same "minimal scroll" rule the browser uses for its own selection, §5.2) — not necessarily to the top of the viewport.
  - An empty query, or a query with zero matches, still records the query and clears any prior matches (so the file title bar reflects "no matches" rather than silently doing nothing).
  - **Plain-text tier** (§2.1): since that tier never holds the whole file resident, locating matches can't happen synchronously against an in-memory line list the way it does for the highlighted tier — Return instead starts a background, cancelable scan of the file (mirroring the same streamed-line, non-blocking shape content search's own background scan already uses, §9.1, rather than a new pattern), and the file title bar's status area shows the query alone until the scan has been running long enough to be perceptible, then a "searching…" spinner (§5.2, §5.3's threshold/frame-rate discipline) in place of a match count until it finishes. Escape while a scan is running cancels it outright (discarding whatever partial progress it had made) the same way Escape clears an idle find — there is no partial/queued result exposed mid-scan. A later query on the same entry (another Return in the prompt) supersedes and cancels any still-running scan for it first. No separate size/time ceiling is imposed on this scan beyond the shared highlighting ceiling that put the file in this tier to begin with — revisit only if real usage shows one is actually needed.
- **`n`**: move to the next match, wrapping to the first match if the current one is the last. A no-op if there's no active find or it has zero matches.
- **`N`**: move to the previous match, wrapping to the last match if the current one is the first. Same no-op conditions as `n`.
- **Wrap note**: stepping with `n`/`N` past either end of the match list sets a transient note ("wrapped to top" or "wrapped to bottom" depending on direction) that's displayed until the next `n`/`N` step, cleared immediately if that next step doesn't itself wrap.
- **Highlighting**: every match is highlighted in the preview content itself, in a style distinct from syntax highlighting and from each other — the current match rendered more prominently than the rest, so it's unambiguous which one `n`/`N` will move from next. Highlighting persists even underneath the open-files-list overlay's read-only view (§2.3), since it's a passive visual, unlike the file title bar's find status/legend, which (like goto-line's legend) is shown only where the preview is actually interactive.
- **Status display**: while a find is active (query non-empty), the file title bar's right-aligned legend area (§5.2) shows the query, the current match's position and total count (e.g. "3/12"), the wrap note if set, and a keybinding legend that always includes `esc` (clear, below) plus — only when there's at least one match — `n`/`N`; a zero-match search shows "no matches" instead of a position/count, with no `n`/`N` in the legend since there's nothing to step between, but `esc` is still shown since it still clears a zero-match find.
- **Escape**, when a find is active: clears it (query, matches, current index, and wrap note), returning the file title bar to its idle content (§5.2) and removing all highlighting. Escape otherwise remains inert at the primary view (§7) — this is its only effect there, it still never quits (only `q` does), and it's a no-op when there's no active find to clear, so it can't be mistaken for a general-purpose "back out" key.

## 3. Browser

The browser is the overlay used to browse the filesystem and open a file into the primary view (§2) — see §5.1 for when it's shown relative to the preview. §3.1–§3.3 cover the supporting data it operates on (the node model, the ignore rules that filter it, and how it's sorted); §3.4 covers the browser's own navigation and open actions.

### 3.1 Core data model

The tool operates over a lazily-loaded tree of filesystem entries rooted at the resolved start path.

Each entry (a "node") has:

- an absolute path
- a display name (the path's basename; for the root, if the basename is empty — e.g. `/` — use the full path string instead)
- a depth (root is depth 0, children are parent depth + 1)
- a parent reference (root has none)
- whether it's a directory
- an expanded/collapsed state (directories only; starts collapsed except the root, which starts expanded)
- a lazily-populated children list (`null`/`None`/unset until first loaded; loading is idempotent — loading an already-*successfully*-loaded node's children is a no-op)
- an optional error string, set when the node's directory entries could not be listed (e.g. permission denied); on error, treat the node as having zero children rather than propagating an exception, and render the error inline (see §5.2). Unlike a successful load, a failed load is *not* treated as done: the next attempt to load that same node's children (e.g. the user collapses and re-expands it, §3.4) re-lists the directory rather than silently no-oping and leaving the stale error in place forever — so fixing the underlying problem (e.g. restoring read permission) and retrying actually clears it, not just a live-refresh (§6.1) happening to pick up the fix on its own. A failed expand also leaves the directory's expanded state untouched (still collapsed/fully undisclosed, §3.4) rather than marking it expanded onto zero children — there's nothing to disclose, and staying collapsed is what makes every subsequent attempt retry rather than being treated as "already expanded, nothing to do."

**Root node initialization:** on startup, build the root node, load its `.gitignore` (see §3.2), load its children, and mark it expanded.

**Flattening (visible list):** the browser operates over the currently-visible, depth-first, pre-order flattening of the tree: the root, then — if the root is expanded — each child's own flattening, recursively. A node's subtree contributes to this list only while every ancestor down to the root is expanded. This is "progressive disclosure": collapsed directories hide their descendants from the visible list (and from on-screen rendering) but the descendants still exist in the lazily-loaded tree once visited.

### 3.2 Traversal and ignore rules

Three independent exclusion mechanisms apply identically to (a) normal directory listing/expansion and (b) the background full-tree index used by quick open and content search (§4.1). Jump to file (§4.3) needs no separate mention here since it matches only against rows the (already-filtered) interactive tree is already showing:

1. **Always skip `.git`** (exact name match on any path segment's immediate entry, not a pattern) — unconditionally, regardless of `.gitignore` contents. Git internals are never useful to browse or search and can be large.
2. **`.gitignore`-aware filtering**, best-effort:
   - At root-node construction, look for a `.gitignore` file directly in the root path. If present and readable, parse it into an ignore-pattern set (see the matching algorithm below). If absent, unreadable, or pattern-parsing isn't implemented for a given rule, treat it as "no additional patterns" — never crash or block startup because of a malformed `.gitignore`.
   - When listing a directory's entries (or walking the full tree for the index), drop any entry that matches the loaded pattern set, so an ignored directory's contents are never even enumerated (not just hidden after listing).
   - Only the root's `.gitignore` needs to be honored. (The prototype did not walk nested `.gitignore` files in subdirectories; parity does not require it, though an implementation may choose to go further.)
3. **`.dirtreeignore`-aware filtering**, an application-specific exclusion list independent of `.gitignore`, applied identically everywhere `.gitignore` is (browser listing, index walk — never just quick open; a path either exists in the app or it doesn't):
   - At root-node construction, look for a `.dirtreeignore` file directly in the root path, alongside the `.gitignore` lookup. Same syntax, same best-effort tolerance (missing/unreadable/malformed → "no additional patterns," never crash or block startup), same "only the root's file is honored" scope.
   - A candidate path is excluded if it matches *either* the `.gitignore` pattern set *or* the `.dirtreeignore` pattern set. The two files' patterns don't interact with each other — a `!negation` in one cannot re-include a path the other excluded; negation precedence (this section's "later rules override earlier ones") only applies within a single file's own rule list.
   - Rationale: this exists for exclusions that are about dirtree's own browsing noise (e.g. build output you don't want fuzzy-findable) rather than about what git tracks, so it shouldn't require touching a repo's actual `.gitignore` (or exist in a repo without one at all).

**Minimal gitignore pattern semantics to implement** (a small, dependency-free subset — this does not need to be a full `git check-ignore` reimplementation, but must at least cover):
   - Blank lines and lines starting with `#` are ignored (comments).
   - A pattern with no `/` matches the basename at any depth (e.g. `*.log` matches `a.log` and `sub/a.log`).
   - A pattern containing `/` (other than a trailing slash) is anchored to the root (matches only starting from the tree root, not at arbitrary depth).
   - A trailing `/` means "match directories only."
   - A leading `!` negates a previous match (re-includes a path that an earlier pattern excluded). Later rules override earlier ones, matching git's actual precedence.
   - Glob wildcards `*`, `?`, `[seq]` behave as shell globbing (not needing to also support `**` recursive-glob semantics for parity, though it's a reasonable enhancement).
   - When testing a candidate path, match it against its path relative to the tree root, POSIX-slash-delimited; append a trailing `/` to the tested string when the candidate is itself a directory, so directory-only patterns work.

### 3.3 Directory listing order

Within a directory, entries are sorted directories-first, then case-insensitively by name.

### 3.4 Navigation semantics

State: a `selected` index into the current flattened/visible list, and a `scroll` offset (topmost visible row index) used only for rendering (§5.2).

- **Up / Down**: move `selected` by ∓1, **wrapping around** at both ends (moving up from the first visible row selects the last; moving down from the last selects the first).
- **Right**:
  - On a directory that is currently collapsed: expand it (load children if not already loaded) and mark it expanded. Selection does not move. If loading fails, the directory stays fully undisclosed — not marked expanded, since there's nothing to disclose (§3.1) — and briefly flashes red with the failure appended inline (§5.3, §6.1) as feedback that the attempt just failed; every subsequent Right on that same still-broken directory retries the listing and flashes again, not just the first attempt, since "expanded" never got set the first time.
  - On a directory that is currently expanded and has at least one child: move selection to its first child.
  - On a directory that is expanded with zero children, or on a file: no-op.
- **Left**:
  - On a directory that is currently expanded: collapse it in place. Selection does not move (stays on the now-collapsed directory).
  - On a directory that is currently collapsed and has a parent: move selection to its parent.
  - On a directory that is collapsed with no parent (i.e. the root): no-op.
  - On a file: move selection to its parent directory **and collapse that parent**, in the same keypress (i.e. "go up and close" in one step, not two).
- **Page Up / Page Down**: move `selected` by a full visible-list-height jump instead of one row at a time, clamped at the first/last row rather than wrapping (the same "jump by a page, don't wrap" convention quick open's, §4.2, and the open-files list's, §2.3, own Page Up/Down use).
- After any structural change (expand/collapse/move), if the previously-focused node object is still present in the newly-flattened list, keep it selected (find it by identity, not by recomputing an index formula) — this matters because expand/collapse changes how many rows precede a given node.
- **Return**: on a directory, disclose it — toggle its expand/collapse state, loading children on expand if not already loaded; a failed expand attempt is handled identically to Right's own failure case above (undisclosed, red flash, retried on every subsequent attempt). On a file: open it (§2.2's open semantics) and display it in the primary preview view, leaving the browser overlay open and selection unchanged, so several files can be queued up in a row without leaving the browser. If the result is "failed" (read error or binary), see §2.2's open-failure signaling — the browser stays open regardless, so the only visible effect is the inline message.
- **`/`**: enter jump-to-file mode (§4.3) to reveal/select a file or directory within the browser itself, without leaving the browser view — the row list stays on screen and live-tracks the query as you type. Escape reverts the browser's selection to whatever it was before `/` was pressed and leaves jump mode.
- **`o`**: open quick open (§4.2), replacing the browser view while it's active; Escape returns to the browser unchanged, while opening a match lands on the primary preview view instead (§4.2).
- **Escape**: close the browser overlay and return to the primary preview view unchanged (whatever was displayed, or the empty state, stays as it was). `b`, the key that opens the browser from the primary preview view (§7), has no effect while the browser is already open — Escape is the sole close key.

## 4. Quick open and jump to file

Two features share the name "search for a path," but are otherwise unrelated in mechanism: **quick open** (§4.2), reachable only from the primary preview view (browse, quick open, and content search are mutually exclusive, §5.1), is a full-screen overlay that searches the *entire* tree via a background index and opens a matched path into the open-files list. **Jump to file** (§4.3), reachable only from within the browser, is not an overlay at all — it's an in-place typing mode of the browser itself, matching only against rows the browser's current expand/collapse state already exposes, and moving the browser's own selection live as you type. They used to share a background index and matcher; they no longer do, since jump to file's whole premise is now that it only ever considers what's already disclosed on screen. §4.1 covers the background index quick open (and content search, §9.1) search; §4.2 covers quick open; §4.3 covers jump to file.

### 4.1 Background full-tree index

Quick open (§4.2) and content search (§9.1) need to search the *entire* tree regardless of what's currently expanded, but building that list can be slow on a large tree if done synchronously when it's first opened. So:

- Immediately at startup (after the root node is built), kick off building a **background index**: a flat, recursively-walked list of every path under the root (files and directories, root itself excluded), applying the same skip/ignore rules as §3.2, sorted by its root-relative slash-delimited display path, case-insensitively.
- This must run concurrently with the UI being immediately usable (i.e. the browser must not block waiting for the index).
- The index-building walk must guard against symlink cycles (track resolved/canonical real paths already visited; do not re-descend into one already seen).
- The index-building process must not share mutable state with the interactive tree's node objects — it operates on raw paths only, so no locking is required between the UI thread/task and the indexing thread/task. (This is a correctness requirement, not a style preference: the prototype found that reusing the same mutable node objects across threads was a real data-race hazard and redesigned around it. Whatever concurrency model the implementation language provides — OS threads, green threads, async tasks — the two must not touch each other's mutable state.)
- Track whether indexing has completed and how much time has elapsed since it started; both are needed for the delayed-loading-indicator behavior in §4.2 and §5.2.

**Matching**, used by quick open: an empty query matches everything. A non-empty query:

- If it contains any shell-wildcard character (`*`, `?`, `[`), it's matched via case-insensitive shell-glob matching against the *entire* candidate string.
- Otherwise, it's a case-insensitive **substring** match against the same candidate string. (This is deliberate: most quick-jump queries are typed as plain fragments, not `*fragment*`, and requiring wildcard wrapping for the common case would be worse UX.)
- Matching runs against the *entire tree's* index, not just currently-expanded/visible nodes or currently-open files — quick open is global regardless of any other UI state. (Jump to file, §4.3, uses an unrelated, simpler matching rule scoped to what's currently visible in the browser.)

### 4.2 Quick open

Triggered by `o` from the primary preview view (§2.1), including while it's showing the empty state, replacing it. Browse, quick open, and content search are mutually exclusive (§5.1): `o` has no effect from within the browser or content search overlays, so reaching quick open from either of those requires closing back to the primary preview view first. Unlike the browser, quick open is not a toggle on its trigger key — `o` is a live filter character once the overlay is open (a common enough letter that overloading it as a close key would break ordinary typing) — so Escape returns to the primary preview view, unchanged; opening a match, by contrast, always lands on the primary preview view too, the same as content search (§9.2).

- The primary preview view is fully replaced by a **flat list view**: every non-directory entry from the background index (§4.1), rendered as its root-relative, slash-delimited path (not the browser's indented/marker style) — this is what makes it distinct from the browser, and lets a query match on any path segment, not just a leaf name. Directory entries in the index are never shown as their own row here — there's no action to take on one, since Return can only open a file into the open-files list — but a query still matches against a file's full path, so typing a directory-name fragment (or segment further up the path) still narrows the list to files under it exactly as before; only the directory's own row is omitted. Each row carries the same "●"-vs-blank open-file indicator the browser (§2.2) and content search (§9.2) rows already do, inline immediately before the path: a match already present in the open-files list (opened from quick open itself, the browser, content search, or earlier in the session) shows the marker; one that isn't shows a blank placeholder space in its place instead, so the path's own starting column stays aligned either way.
- A query string starts empty and accumulates/removes characters as the user types/backspaces. It is shown on its own input row directly below the header (see §5.2). Once the background index (§4.1) has finished building, that same row's right side shows a `N of N files` summary — how many of the index's files (directories excluded) currently match the query, out of its total file count — the same left-text-plus-right-aligned-content composition content search's own query-row hit summary uses (§9.2); it's absent while the index is still building, since neither number is meaningful yet.
- **While the background index has not finished building**: matches are empty/unavailable; render the delayed loading indicator described in §5.2 instead of "no matches" (don't claim there are no matches when you simply haven't looked yet).
- A `selected` index into the current match list, with wraparound cycling: advance forward (Down) or backward (Up). Page Up/Page Down move the selection by a full match-list-height jump instead of one row at a time, clamped at the first/last match rather than wrapping (the same "jump by a page, don't wrap" convention the open-files list's own Page Up/Down uses, §2.3).
- **Return**, if there is at least one match: open the selected match's path into the open-files list, per §2.2's open semantics (reusing an existing open-files entry if the path is already open). If the result is "opened," close the overlay, landing on the primary preview view with that file displayed. If the result is "failed" (read error or binary), see §2.2's open-failure signaling — the overlay stays open with the message shown inline instead of exiting. On success, the browser's disclosure state is also updated to reveal the opened path — every intermediate ancestor directory is expanded and the browser's selection moves to it — so opening the browser afterward (`b`) shows where that file lives without further navigation; this is distinct from jump to file (§4.3), which deliberately never expands anything, since quick open (like content search, §9.2) searches the whole tree regardless of what's currently disclosed and so has no other way to reflect what it just opened.
- **Backspace**: remove the last character of the query; reset match-selection to the first match and reset scroll.
- **Ctrl+U**: clear the entire query (§7); reset match-selection to the first match and reset scroll, the same as Backspace above.
- **`o` / Escape**: cancel the overlay and return to the primary preview view, unchanged (query and match selection are discarded; no action is performed).
- Typing any other printable character appends it to the query (reset match-selection and scroll to the top, since the match set changes).

### 4.3 Jump to file

Triggered by `/` from within the browser overlay (§3.4) — jump to file has no entry point of its own from the primary preview view; the browser must already be open. Unlike quick open, jump to file is **not** an overlay and does not replace anything: the browser's row list stays on screen exactly as before, and jump to file is simply a typing mode layered on top of it that repurposes every printable key as query input instead of a browser command. The point is to let the user navigate by typing instead of by arrow keys while staying fully in control of which directories are expanded — jump to file never *collapses* anything on the user's behalf, and only ever expands via the one explicit, deliberate exception below (slash-to-expand); otherwise it only ever selects among rows the browser is already showing.

- **Candidate set**: the current flattened row list (§3.1) of the jump **scope** — every row visible given the tree's *current* expand/collapse state, files and directories alike, under the scope node. The scope starts as the tree root on entering jump mode (so the candidate set is initially the same as the browser's whole current row list) and narrows to a directory via slash-to-expand (below). This is recomputed live: if the query, an earlier Tab/cycle, or anything else has already moved the browser selection to a different row before further typing, the candidate set still reflects whatever is currently disclosed under the current scope (jump to file itself never collapses anything, so in practice this only matters if disclosure changed some other way while jump mode was open, which it can't be — no other browser keys are live during jump mode, per below — or if the scope itself just changed via slash-to-expand).
- **Matching**: a case-insensitive **prefix** match of the query against each candidate row's own leaf name (its `Name`, not its full path — jump to file is about picking out something you can see printed on screen, not searching a path). An empty query matches nothing in particular (see below).
- On entering jump mode (query empty): the browser's current selection and scroll are remembered so Escape can restore them; no match is highlighted yet and the browser selection does not move until the first character is typed.
- Typing a printable character appends it to the query and recomputes matches; if the new match set is non-empty, the browser's selection immediately jumps to the first match in display (top-to-bottom) order, scrolling it into view exactly as arrow-key navigation would. If the new match set is empty, the browser selection is left wherever it currently is — an unmatched query does not move or lose your place.
- **Slash-to-expand**: if, at the moment `/` is typed, the current match set contains **exactly one** row and it is a directory, `/` is not appended to the query as a literal character (which could never match anything anyway, since no filename contains `/`). Instead: that directory is expanded (loading its children if needed, the same as the browser's own Right-arrow expand, §3.4), the query — which just named this directory — plus a trailing `/` is appended to a running **disclosed-path prefix** that's kept separate from the query, the query itself resets to empty, the jump scope narrows to that directory (so the candidate set and all further matching become just its descendants, not the whole tree), and the browser selection moves to it. The disclosed-path prefix renders ahead of the (now-empty) query on the query's own input row (§5.2), so committing a segment this way reads as "type the next part" rather than "my typing just vanished." This can be repeated to drill down multiple levels in one jump-mode session (match a name, `/`, match a name under it, `/`, and so on — the prefix accumulates each committed segment, e.g. `internal/ui/`). If the directory fails to load (permission error, etc.), it is left fully undisclosed exactly as a failed Right-arrow expand would be (§3.1), the same red row-flash is shown, and the query/scope/disclosed-path prefix are left unchanged — the `/` keystroke is simply absorbed, neither appended nor triggering a scope change. Backspacing back to an empty query afterward does not undo the expansion, re-widen the scope back out, or remove anything from the disclosed-path prefix — once a directory has been expanded this way it stays expanded and stays the active scope for the rest of the jump session, the same as quick open's own expansions are never undone by cancellation elsewhere (§4.2). The disclosed-path prefix is purely a display aid — it plays no role in matching — and is reset (to empty) each time jump mode is freshly entered.
- **Backspace**: removes the last character of the query and recomputes matches the same way (jumping to the new first match, or leaving selection in place if none). Backspacing does not change the jump scope (see slash-to-expand above).
- **Ctrl+U**: clears the entire query (§7) and recomputes matches the same way as Backspace above.
- **Tab / Down**: if there is more than one current match, moves the browser selection to the next match after the currently-selected one in display order, wrapping around to the first after the last.
- **Shift-Tab / Up**: same, in the reverse direction.
- **Return**: leaves jump mode with the browser selection exactly where it is (whatever the query/cycling last landed it on) — it performs no further action; the browser's own Return (§3.4) can subsequently be pressed to open the file normally.
- **Escape**: leaves jump mode and restores the browser's selection and scroll to what they were before `/` was pressed, discarding the query — a true cancel.
- While jump mode is active, no other browser key (`b`, arrows, `Return`'s open action) is live — every rune is query input, and only the keys listed above are otherwise recognized, so a query can safely contain any letter (including `/`, `o`, `s`, `b`) without triggering a browser command.
- Jump to file does not depend on, and is not gated by, the background index (§4.1) — it operates purely on the already-loaded interactive tree, so there is no indexing/loading state to show here the way there is for quick open (§5.2).

## 5. Visual layout and rendering

### 5.1 View model and overlay layout

The **primary preview view** (§2.1) is the default screen: on startup it shows the empty state, with no overlay active (§1); once at least one file has been opened, it shows that file (or whichever was most recently made the displayed entry) whenever no overlay is active. Emptying the open-files list at runtime — e.g. removing its last entry, §2.3 — lands on this same empty state exactly the same way startup does, with no overlay auto-opened on top of it either.

Three overlays exist, and each is closed by Escape back to the primary preview view: the **browser** (§3), **quick open** (§4.2), and **content search** (§9), plus a fourth, the **open-files list** (§2.3), that follows the same rule. Only one overlay is active at a time, and browse, quick open, and content search are additionally mutually exclusive with each other: all three are reachable only from the primary preview view, never from one another, so getting from one to a different one always means closing the first (Escape) back to the primary preview view and then opening the next. This is deliberate — each of the three is a distinct way of picking a file to open, and letting one launch directly into another made it easy to lose track of which mode's state (a browser selection, a quick open query, a search) you were about to abandon. The open-files list (§2.3) is exempt from this — it's not one of the three file-selection modes, just a dropdown over the current session's open files — and remains reachable only from the primary preview view regardless. Escape is the sole close key for all three: `b`, the key that opens the browser (§7), has no effect once the browser is already open, and `o` is likewise not a toggle on quick open — once it's open, `o` is a live filter character like any other (§4.2). Jump to file (§4.3) is not an overlay — it's an in-place typing mode of the browser that never replaces the screen, so it isn't counted here; it's only reachable while the browser overlay is already active and doesn't change which overlay is active.

**Browser layout**: like quick open (§4.2), the browser always fully replaces the screen at every terminal width — a header row (mode label plus keybinding legend) and the flat row list filling the rest of the screen below it. The primary preview view underneath is not visible while the browser is open; it resumes showing whatever it had (or the empty state) once the browser closes. (An earlier version of this spec had the browser render as a split view alongside a read-only preview pane on wide terminals, or a centered popup over the unmodified preview on narrow ones. That dual layout was removed: the split-view preview pane was never a live preview of the browser's selection — it just kept showing whichever file had last been opened, static, until Return opened something new — so its real value was narrow ("reference the currently-open file while picking the next one"), and it carried a recurring cost of its own: two separate draw paths and a layout-threshold computation, and a class of "two regions share a row" bugs at the pane boundary. Full-screen-always trades away that narrow wide-terminal benefit for one draw path and no threshold to get wrong.)

### 5.2 Rendering conventions

- **Header/title bar**: a single full-width row at the very top of the screen, rendered with a background contrasting from the normal row background *and* from the reverse-video selection highlight (so the title bar is never visually indistinguishable from a selected row directly beneath it — the prototype initially made this mistake using plain reverse-video for both and had to give the title bar a distinct fixed color pair instead). Content:
  - Primary preview view, and — since it doesn't replace this row, only pops up over it (§2.3) — the open-files-list overlay too: the tree root path — never the path of whatever file happens to be open (see the separate per-file title bar below) — left-aligned, and a short keybinding legend, right-aligned, with at least one space of separation between them. The root path is abbreviated with common shell shortcuts where applicable (e.g. `~/dirtree` instead of `/Users/x/dirtree`) to save space, and is recomputed, and re-fit, every frame so a live resize is reflected immediately. This legend lists only app-wide actions (navigation between views/overlays, quitting); actions specific to whichever file is currently displayed (e.g. goto-line) do not belong here — see the file title bar below. The `switch files` entry (§2.3) renders dimmed whenever the open-files list is empty, since Tab then has nothing to switch to or from — it stays in the legend rather than disappearing (so the keybinding hint doesn't flicker in and out as files are opened and closed), just visually deprioritized against the rest of the row; it returns to its normal weight the moment at least one file is open.
  - **Narrow-terminal fit/drop order**: every legend in the app (this header/title bar, the file title bar below, the open-files-list dropdown's own header, and every overlay's own mode header) is an ordered list of keybinding entries, each tagged with a drop priority (1 highest/never dropped, 3 lowest/dropped first). The left-hand content shown alongside the legend (root path, mode label, file path, or similar) shares that same drop order at an effective priority of "2.5": weaker than every priority-2 entry, but stronger than any priority-3 entry, so it is dropped only once every priority-3 entry already has been, and before any priority-2 entry is. Concretely, at a given width the first of these that fits wins: (1) left-hand content plus the full legend; (2) left-hand content plus the legend with priority-3 entries dropped; (3) the legend alone (no left-hand content) with priority-3 entries dropped; (4) the legend alone with priority-2 entries dropped as well, leaving only priority-1 entries — used as a last resort regardless of whether it actually fits. The legend itself is always right-aligned, flush with the row's right edge, whether or not the left-hand content is present — when both are present, any unused width beyond the required one-space separation is added to the gap between them, pushing the legend further right rather than leaving it immediately after the left-hand content; when the left-hand content is absent, the legend is padded on its own left with enough blank space to reach the same right edge. This keeps the legend's own reading position consistent — it never visibly jumps from right-aligned to left-aligned (or the reverse) depending on whether the left-hand content happens to be present at a given width. All four states above are recomputed every frame, so a live resize can restore anything dropped once there's room again. This ordering means a disposable priority-3 key hint (e.g. `[ctrl+u] clear`) is sacrificed before the root path or mode label is — losing that context is a bigger loss than one low-value legend entry, so it's worth trying to buy back room from the legend first. Dropping only ever removes whole entries; it never reorders the survivors and never truncates an individual entry's text mid-way. Every legend's priority-1 subset, on its own with no left-hand content, must fit within §6.4's minimum terminal width — that floor exists precisely so nothing below it renders at all, and a priority-1 entry list that could still overflow at exactly the minimum would defeat that guarantee; an entry whose text is long enough to risk this (e.g. one naming a two-key alternative like Tab/Shift-Tab) is a signal to demote it to priority 2 rather than to raise the minimum width to accommodate it.
  - **Mode name**: whenever the header/title bar's left side shows anything other than the tree root path, it renders as a bold, all-caps mode label (e.g. `BROWSE`, `QUICK OPEN`, `SEARCH`) rather than plain-weight text — analogous to a modal text editor (e.g. `hx`) always surfacing its current mode — so the active mode reads at a glance and is visually distinct from the legend that follows it on the same row, which stays normal weight regardless. The label follows the same fit/drop rule the root path uses: if the terminal is too narrow to fit both the label and the legend, the label is dropped in favor of the legend alone, recomputed every frame.
  - Browser overlay, not jump to file: this row is the browser's own header, showing the `BROWSE` mode label plus the browser's own keybinding legend (Return open, left/right expand/collapse, `/` jump to file, Escape close).
  - Quick open overlay: the `QUICK OPEN` mode label and a short keybinding legend (Return opens the selected match, Page Up/Down move the selection by a page — up/down move it by one row via the arrow keys, already covered without a dedicated legend entry — Ctrl+U clears the query, Escape cancels); the literal query typed so far is shown on its own input row directly below the header instead (the same input-row convention content search uses, §9.2), not in the header itself.
  - Browser overlay while jump to file (§4.3) is active: the mode label stays `BROWSE` — jump to file is a typing mode layered on the browser (§4.3), not a distinct mode of its own — but the legend switches to jump mode's own short keybinding legend (Return done, Tab/Shift-Tab next/previous match, `/` slash-to-expand, Ctrl+U clears the query, Escape cancels). The literal query never appears in the header/title bar itself — user-entered text has no place in a mode-name row — it instead renders on its own input row directly below the header, prefixed `> ` the same input-row convention quick open and content search use for their own queries; any path segments already committed via slash-to-expand render ahead of the live query on that row (e.g. `> internal/ui/rend`) so disclosing a directory doesn't read as erasing what was already typed — see §4.3. This row is confined to the browser's own width like the rest of the browser overlay.
  - Open-files-list overlay's own dropdown box (as opposed to the header/title bar above, which stays on the primary preview view's own content per the bullet above): its top border carries the "open files" title, embedded the same way a bordered popup embeds its own title in its border; a content row directly inside the box shows the page range counter (e.g. "11–20 of 23") left-aligned and the dropdown's own keybinding legend right-aligned, same fit/drop convention as the header/title bar; and the box's top/bottom border additionally carries a "▲"/"▼" glyph when a previous/next page exists, per §2.3.
- **File title bar**: a second full-width row, directly above the preview content and visually distinct from both the header/title bar above it and the preview content below it, shown only while a file is displayed (the empty state has no file title bar, since its explanatory hint already occupies the content area) — present wherever the preview content itself is rendered: the primary preview view, and underneath the open-files-list overlay's dropdown (§2.3). Left-aligned, it renders the displayed entry's total line count (e.g. `120 lines`, singular `1 line` for a one-line file) followed by that entry's root-relative, slash-delimited path (the same path-rendering convention as quick open, §4.2, and the open-files list, §2.3) — this is where the open file's own identity lives now that the header/title bar above is reserved for the tree root. The line count is exact once known: immediately for a `TierHighlighted` entry (`len(Lines)`, already resident), or once the background line-offset pass (§2.1) finishes for a `TierPlainText` entry; while that pass is still running, it shows the count of lines streamed so far, which grows live as the pass progresses rather than staying pinned at a placeholder. This count-plus-path prefix participates in the same left-hand-content-at-priority-"2.5" fit/drop rule as the rest of this row's left side (§5.2's header/title bar bullet above): it is dropped along with the path, as one unit, never independently. Right-aligned (same fit/drop rule as the header/title bar above, keyed off this row's own width), it renders a keybinding legend of actions specific to the displayed file — in-file find (`/`, §2.4), goto-line (`g`), and copy mode (`c`, §2.1) — but is the designated home for any file-specific action added in the future, so the header/title bar's legend stays app-wide-only. While the displayed entry's background line-offset pass (§2.1) is still running and has crossed the perceptibility threshold, `[g] goto line` is replaced with a "building…" spinner (§5.3), and pressing `g` anyway briefly flashes this row red with an inline "still indexing, try again shortly" message in place of the path/legend, the same red-flash-plus-inline-message convention used for a failed file open (§2.2) — see §2.1 for the full block/allow behavior this reflects. This legend is only shown where the preview is actually interactive: it's omitted (path only) underneath the open-files-list overlay, since the preview there is read-only while that overlay owns input and advertising a key that currently does nothing would be misleading. While in-file find has an active query, this same row's left/right split instead shows the in-file find prompt (while typing) or its live status (query, match position/count, wrap note, and a next/previous legend — §2.4) in place of the path and goto-line/find legend, in both cases only where the preview is interactive; underneath the open-files-list overlay it still shows just the path even with an active find, though the matches themselves remain highlighted there regardless (§2.4's highlighting is passive and always shown). While the displayed entry is in copy mode, the left side is tagged `[copy mode] ` ahead of the path (or ahead of whichever other left-side content — the find prompt or an active find's status — is otherwise showing there, so the tag stays legible no matter which of this row's other states copy mode happens to be layered under), the legend shows `[c] normal view` in place of `[c] copy mode` in the idle case specifically (goto-line and find are additionally omitted there, though still reachable by key, the same way arrow-key scrolling is never listed either), and the row itself renders in a visually distinct style — this style change, unlike the legend text, is not gated on interactivity, since copy mode's plain-rendering effect on the preview content itself applies everywhere that entry's preview is drawn, interactive or not (§2.1).
- **Selected row**: rendered in reverse video (or an equivalent single, consistent "selected" visual treatment) relative to unselected rows.
- **Jump-to-file match highlighting** (§4.3): while jump mode is active with a non-empty match set, every currently-matching row in the browser gets a distinct highlight (reusing in-file find's non-current-match style, §2.4, is sufficient) so the full set of candidates is visible at a glance, not just the one currently selected; the selected row's own highlight (above) takes precedence where the two would otherwise overlap, since it's always one of the matches while jump mode is active.
- **Directory expand/collapse marker**: a small glyph before the name distinguishing expanded vs. collapsed directories (a down-caret vs. right-caret, e.g. `▾`/`▸`) — the same glyph pair every view showing this indicator uses (the browser here and content search's own file rows, §9.2), so it reads as one consistent concept rather than a per-view convention; files get equivalent blank spacing so names still align vertically.
- **Browser open-file indicator and flash** (§2.2, mirroring content search's own file rows, §9.2): a browser row for a file already in the open-files list (whether opened from the browser itself, quick open, content search, or earlier in the session) shows a lasting "●" indicator inline between the expand/collapse marker and the name (directories never show it, only files can be open); pressing Return on a row that opens it (§3.4) also briefly flashes that row in a distinct style — the same one-shot "this Return just opened something" confirmation content search's Return gives its own file rows — before it fades back to normal after a short, fixed duration, purely visual and never blocking input. Unlike content search, where the flash and the cursor's own highlight can land on two different rows (a hit row can be selected while its parent file row flashes), the browser's Return never moves the selection (§3.4), so the flashing row and the selected row are always the same one; the flash takes precedence over the selected-row highlight for its brief duration here specifically, the opposite of the jump-to-file match highlight's precedence above, since giving the reverse-video selection style precedence in this case would permanently mask the flash and make it invisible.
- **Indentation**: each row is indented proportionally to its depth in the tree, so the hierarchy is visually legible.
- **Per-node error indicator**: if a node failed to list its children (see §3.1), append a bracketed short error string after its name.
- **Delayed loading indicator** (indexing spinner / badge): while the background index (§4.1) has not finished, an animated spinner is available for use in two places — a small floating badge anchored to the bottom-right corner of the screen, rendered in **every** view (the primary preview view and every overlay — browser, quick open, content search, and the open-files list — so the badge's sequence below stays visible/watchable no matter which one is currently showing, including simply sitting on the primary preview view without having opened any overlay yet), and, in quick open specifically, also replacing the match list entirely with an "indexing…" message. (Jump to file, §4.3, doesn't use the background index at all, so it has no indexing-dependent state and doesn't participate in any of this.) The content search overlay (§9) renders the same bottom-right badge (it depends on the same background index for its candidate set) but has its own "indexing…"/"searching…" results-area placeholder per §9.1, distinct from quick open's — and unlike theirs, content search's own scan (not just the background index) also gets an animated spinner glyph once it's been running long enough to be perceptible, since a content scan can itself be slow (a broad regex over a large tree) independently of whether the index is done. In both cases, **suppress the indicator entirely until the relevant work has been running for at least a short threshold** (250ms in the prototype). This is a deliberate UX fix: on a small tree, indexing finishes in a handful of milliseconds, and briefly flashing a spinner for genuinely instant work reads as more distracting than informative — so nothing is shown at all until it's clear the wait is actually perceptible. During that sub-threshold grace period in quick open specifically, render neither the spinner nor a "no matches" message in the match-list area (since indexing not being done yet is a different state from "genuinely zero matches") — just leave the match-list area blank; the corner badge follows its own sequence below independent of the match-list area's blank state.
  - Compute the spinner glyph by cycling a small fixed set of animation frames at a fixed rate (10 frames/sec in the prototype) driven by elapsed wall-clock time since indexing started, not by frame count, so its speed is independent of render/poll rate.
  - The bottom-right badge is rendered with a background that contrasts with the surrounding rows (an accent color in the prototype), the same "must read as visually distinct" rule the header bar (above) follows — not plain/default-styled text sitting over the view, which is easy to miss in a busy screen.
- **Bottom-right badge sequence**: the badge (unlike quick open's match-list-area indicator, which is just shown/hidden per the threshold above) runs through a full sequence once indexing has crossed the perceptibility threshold, identically regardless of which view is currently on screen (the primary preview view, the browser, quick open, content search, or the open-files list):
  1. **Spinner**: shown as soon as the threshold is crossed, animating as described above.
  2. **Minimum display duration**: the spinner stays on screen for at least a short minimum duration (1 second in the prototype, measured from when indexing started) even if indexing genuinely finishes sooner — real directories often index in microseconds, so without this floor the spinner could cross the threshold and finish in the same frame, an unreadable flash rather than a perceptible indicator.
  3. **Completion message**: once both indexing has actually finished and the minimum display duration has elapsed, the spinner is replaced with a transient "indexing complete" message, shown in full for a short display duration (2 seconds in the prototype).
  4. **Fade-out**: the completion message then fades out over a shorter fade duration (on the order of a few hundred ms) by disappearing left-to-right — its earliest characters vanish first while its right edge stays anchored at the same screen position the spinner occupied — until nothing remains.
  - If indexing finishes before ever crossing the perceptibility threshold, none of this sequence runs at all — the spinner was never shown, so announcing its completion would be exactly the flashing-chrome-for-instant-work problem the threshold exists to avoid.
  - **Opening quick open short-circuits the minimum display duration**: if the user opens it while indexing is already done, they've directly seen indexing is ready — the overlay renders the real match list immediately once done, per §4.2. Continuing to hold the badge on step 1's spinner for the rest of step 2's minimum duration at that point would be actively misleading (claiming to still be working on something the user just saw finish), not a perceptibility safeguard, so opening quick open while already done drops the minimum-display-duration floor entirely and treats *the moment the overlay was opened* — not the index's actual (possibly long-past) completion time — as when indexing finished, restarting steps 3/4 fresh from there. Because the badge renders in that overlay too, this transition is immediately visible right there without needing to return to the browser first. This distinction matters in particular for the debug-only always-show mode below: without it, the index's real completion time could already be well past the completion message's entire display+fade window (having been masked the whole time by the artificially-held spinner), and using it directly would make the badge vanish the instant the overlay opened instead of visibly transitioning to the completion message. This short-circuit resets the next time a new indexing cycle starts (e.g. a live-refresh-triggered rebuild, §6.1), since the flash-prevention floor is meaningful again for that fresh run.
  - This whole sequence is specific to the badge; quick open's replacement of the match list is not affected by any of it — once indexing is actually done, the real match list should render immediately rather than being delayed by a completion message.
- **Debug-only always-show mode**: a build-time-only switch (never a runtime flag, and never enabled in a shipped build) that bypasses only step 1's perceptibility threshold — the spinner appears the instant indexing starts — while every other step of the sequence above (the minimum display duration, the completion message, the fade-out) behaves exactly as it otherwise would. This lets the full sequence be watched on demand without needing to reproduce a genuinely slow index. This must not affect quick open's indexing-blocked state, since forcing that indefinitely would make it permanently unusable in a debug build.

### 5.3 Animation principles

The bottom-right badge's completion-message/fade-out steps above (§5.2, steps 3-4) are implemented as a standalone **toast primitive**: "show a transient message in full for a display duration, then fade it out left-to-right from an anchor point over a shorter fade duration" as a pure function of elapsed time (`internal/toast`), independent of what triggered it — factored out so any future transient-message feature can reuse the timing math instead of reimplementing it, though the badge is still the only caller today. A toast was considered for §6.1's newly-erroring-directory case and rejected: an error is diagnostic information the user may need to actually read, and a toast disappearing on its own schedule risks vanishing mid-read — see §6.1's red-flash treatment instead, which draws attention to the error without the error itself decaying.

Any future animation must be designed against the same principles rather than as a one-off:

- **Never block the UI.** No animation may gate input handling, redrawing, or any other work on reaching a particular frame or on a sleep/timer of its own. An animation's state (spinner glyph, fade-out progress, or anything else) is derived fresh at draw time from `(elapsed, done)`-shaped state, the same way §6.2 requires layout itself to be recomputed fresh every frame from current terminal dimensions rather than cached — an animation is just another quantity computed that way, never a separate blocking wait the draw loop has to synchronize with.
- **Informative, not decorative.** An animation must be earning its place by communicating something the user actually needs to know — that background work is in progress, that it just finished, that state changed — not exist for visual polish on its own. If removing it would leave the user no worse informed, it doesn't belong; a dense text UI has no room for chrome that isn't pulling its weight (see `docs/ANIMATION_IDEAS.md`'s tree-expand/collapse and selection-movement examples of this principle ruling an animation out entirely).
- **Elapsed-time-driven, not frame-driven.** An animation's position is a pure function of wall-clock time elapsed since it started, not of how many draws have happened, so its apparent speed is independent of render/poll rate (including §6.2's periodic resize-poll cadence) — and so its logic can be unit-tested with synthetic durations, without a real terminal or real elapsed wall-clock time, per `specs/TESTING.md` and CLAUDE.md's testing discipline.
- **Perceptibility threshold.** Nothing animates for work that resolves before a human would notice — suppress an indicator entirely until the underlying operation has been running for at least a short threshold. Briefly flashing chrome on and then immediately off for genuinely instant work reads as more distracting than informative, not as reassurance that something happened.
- **Minimum-display floor once shown.** An animation that has crossed the perceptibility threshold commits to staying legible for at least a short minimum duration even if the underlying work finishes sooner — without this floor, work that happens to finish just after the threshold could show the indicator for a single unreadable frame instead of a perceptible one.
- **Anchored, directional motion.** Motion reads as happening at a fixed screen position (e.g. §5.2's fade-out disappearing left-to-right while its right edge stays anchored where the spinner was) rather than shifting other content; an animation must never itself trigger a layout recompute.
- **Subtle, not flashy.** Default to the least motion and visual intensity that still communicates the state change — rapid blinking, saturated color flashes, or jarring transitions are distracting in a dense text UI, not more noticeable in a useful way. This applies even where an animation exists specifically to be noticed (e.g. the corner badge): §5.2's contrast treatment — a background that reads as visually distinct from surrounding rows — is what makes it noticeable, not intensity, saturation, or motion; color alone should also be avoided as the sole distinguishing signal, since terminal color support and themes vary.

## 6. System behaviors

These apply across every view/overlay above rather than belonging to any one of them.

### 6.1 Live refresh on filesystem changes

The tree, and the background index (§4.1), must stay current as files and directories are added, moved, or deleted on disk underneath the running session — the user should not have to restart `dirtree` to see a change made by another process (an editor, `git checkout`, a build, etc.).

- The implementation must watch, at minimum, every directory that has already been loaded (§3.1's lazy-loading sense: the root at startup, plus any directory the user has expanded since — jump to file, §4.3, never itself expands a directory, so it never adds to this set beyond what expansion already covers). A directory never visited does not need to be watched — it will simply reflect current disk state whenever it is eventually loaded, same as today.
- Watching must not block or slow down interactive use; detected changes are applied asynchronously, the same way the background index (§4.1) is built without blocking the UI.
- Because change notifications can arrive in rapid bursts (an editor's save-via-temp-file-and-rename is often 2-3 raw events; a multi-file operation like `git checkout` can be dozens), the implementation should coalesce a burst into a single refresh rather than re-scanning once per raw event — a short debounce window (on the order of a few hundred milliseconds) is sufficient and keeps this from being a performance or flicker problem on active directories.
- **Applying a refresh:** re-list each already-loaded directory's contents and merge the result into the existing tree by path, rather than discarding and rebuilding it wholesale:
  - An entry whose path is unchanged (same path, still the same kind — file vs. directory) keeps its existing node identity, and therefore keeps its expanded/collapsed state and any already-loaded subtree, exactly as if it had never been touched.
  - An entry that no longer exists on disk is removed from the tree.
  - A newly-appeared entry is added as a new node (collapsed if a directory, per §3.1's default), sorted into place per §3.3.
  - This mirrors §3.4's existing "keep the previously-focused node selected by identity, not by index" rule — a refresh must not disturb selection or disclosure state for anything that didn't actually change.
- **Selection after a refresh:** if the currently-selected node in the browser was deleted by the change, selection falls back to the nearest ancestor still present in the tree (walking up from the deleted node); the root is always present, so this always terminates somewhere visible. A file that's currently open in the open-files list (§2.2) is unaffected by browser selection fallback — if the underlying file is deleted, its list entry and any loaded preview content simply become stale (see §2.3's removal semantics for what happens if the user then tries to act on it); if the underlying file is merely modified in place, its content is instead reloaded per §6.1a below rather than going stale.
- The background index (§4.1) must eventually reflect the same change (so quick open doesn't keep offering deleted paths or miss new ones — jump to file has no such concern, since it always reads live off the interactive tree rather than a separately-built index). Re-triggering an index rebuild after a live-refresh is treated exactly like the initial index build for purposes of the delayed-loading-indicator (§5.2): a fast rebuild stays invisible, a slow one on a very large tree shows the same spinner/"indexing…" treatment a fresh build would.
- This is best-effort: if the underlying OS change-notification facility is unavailable or exhausted (e.g. a platform inotify-instance/watch-count limit), the implementation must degrade gracefully — continue running with the tree simply not auto-refreshing — rather than failing startup or crashing.
- **Directory-listing-error flash:** any time a directory listing fails, briefly flash that row's background red in the browser (only while it's actually on screen — expanded and scrolled into view; a directory that isn't currently visible gets no special treatment beyond the inline indicator below, picked up whenever it's next scrolled to). Two distinct triggers, with different repeat behavior:
  - A live-refresh discovering an already-loaded directory lost read permission out from under the running session flashes once per *newly*-failing directory in a given refresh (not repeatedly on every debounced refresh tick a persistent, still-broken directory happens to be re-checked by) — every directory that newly failed to list in the same refresh gets its own flash, not just one.
  - The user directly expanding a directory (Right-arrow, §3.4) that fails to load flashes on **every** attempt, including repeated ones on a directory that's still broken from a previous try — since a failed expand never marks the directory expanded (§3.1), each Right-arrow press is a fresh, explicit user action re-attempting the listing, and deserves its own feedback rather than only the first attempt getting one.
  - The row's existing inline `[error]` indicator (§5.2, the same one any listing failure already shows) is what actually communicates the error and does not fade with the flash — only the flash itself is transient, drawing the eye to a row whose error text then stays put for as long as the error persists, rather than risking the diagnostic text disappearing mid-read the way a toast (§5.3) would.

### 6.1a Live reload of open files

An open file's preview content (§2.1) is kept current the same way the tree is, per §6.1: a file open in the open-files list (§2.2) always lives in a directory that's already loaded and therefore already watched, so no separate watch setup is needed to cover it.

- Every open entry is checked on each debounced live-refresh (§6.1), not just the currently-displayed one, so a file open in the background is never stale by the time the user switches to it.
- A change is detected by comparing the file's on-disk mtime against the mtime recorded at the entry's last load or reload — an mtime that hasn't moved is treated as unchanged (no re-read), keeping a refresh with many watched files but few actual content changes cheap.
- Reloading an entry re-reads and re-highlights its content in place (the same read path §2.2's initial open uses, including the byte cap and binary detection) without disturbing the entry's identity, its position in the open-files list, or which entry is currently displayed — reordering never happens as a side effect of a reload. The entry's line-wrap cache and any active in-file find (§2.4) are invalidated, since both are derived from content that just changed underneath them; scroll position is left as-is and simply self-clamps the next time the entry is scrolled into or displayed, rather than being forced back to the top on every small edit — **except** when the reload also changes the entry's highlighting tier (§2.1), in which case scroll is reset to the top instead, since a display-row index doesn't mean the same thing under each tier's model.
- A reload also re-decides the entry's highlighting tier (§2.1) from the file's current on-disk size, using the same `Stat` call already made for the mtime comparison above — not treated as fixed from whenever the entry was first opened. A file that's grown past the ceiling since it was last (re)loaded is demoted to the plain-text tier; one that's shrunk back under it is promoted back to the highlighted tier.
- If the file can no longer be read at all (deleted, permission lost, or now binary), the reload is skipped and the entry's last-known content is left exactly as it was — it goes stale rather than being cleared, per §6.1's existing deleted-file handling above.
- A successful reload surfaces a toast (§5.3) naming the reloaded file(s) (e.g. "`foo.go reloaded (changed on disk)`", with the file name(s) rendered bold so they stand out from the surrounding text at a glance), since — unlike §6.1's directory-listing errors, which are diagnostic text the user may need time to read — this is routine, transient confirmation that's fine to let fade on its own schedule; a burst that reloads multiple open files in the same debounced refresh is reported as one toast listing all of them, not one per file.
- Deleted-file staleness and reload are otherwise best-effort in the same sense as §6.1: if the watcher itself is unavailable, open files simply don't auto-reload, matching the tree's own degraded behavior.

### 6.2 Resize handling

The terminal must be treated as capable of changing size at any time, live, without necessarily receiving a dedicated resize notification — the primary target usage is inside terminal multiplexers (Zellij and similar) that do not reliably deliver resize events to the child process. Therefore:

- The main input-wait must not block indefinitely; it must wake on a short periodic timeout (100ms in the prototype) even with no input, so layout can be recomputed and redrawn on that cadence regardless of whether an explicit resize signal fired.
- Every draw must recompute layout (row/column counts, split-vs-popup decision, pane widths, line-wrap widths) from the terminal's *current* actual dimensions queried fresh each frame — never cache dimensions across frames and trust a resize event to invalidate the cache as the sole mechanism.
- If the implementation's terminal library does deliver an explicit resize event/signal, treat it as a hint to redraw immediately rather than the only trigger to do so.

### 6.3 Escape-key responsiveness

Terminal input libraries commonly buffer a short delay after receiving an Escape byte, to disambiguate a bare Escape keypress from the start of a longer escape sequence (arrow keys, function keys, etc.). Left at defaults, this can make Escape feel like it takes up to ~1 second to register. The implementation must configure its terminal library's escape-sequence timeout down to a short value (on the order of 10–25ms) at startup, before entering the main loop, so Escape reads as instant. (In the prototype, this was set via both an environment variable read at import time and an explicit API call at runtime, to cover two different code paths that read the timeout at different times — whatever the chosen library's equivalent mechanism is, set it early and set it redundantly if the library offers more than one knob for it.)

### 6.4 Minimum terminal size

None of the layouts described above (header + legend, split/popup content, overlays) are designed to degrade gracefully below a floor size — below it, truncating or overlapping content reads as broken rather than merely cramped. The implementation defines a minimum width and height (58 columns × 15 rows in the reference implementation, chosen to keep every legend and layout readable without cramming, and a height that fits the header, file title bar, and a handful of content/legend rows) and checks it fresh every frame, the same way §6.2 recomputes layout fresh every frame rather than caching it. Whenever the terminal is narrower than the minimum width, shorter than the minimum height, or both, a dedicated too-small screen takes over the *entire* frame — superseding the primary preview view and any active overlay alike, with none of their content drawn underneath.

Rather than a block of explanatory text, the too-small screen shows a single undersized dimension as a pair of red arrows pointing apart with that dimension's required size centered between them — a horizontal `← 58 →` on the vertical-center row when width is short, or a vertical `↑` / height-number / `↓` stack centered as a unit when height is short — a direct "stretch this direction to at least this much" instruction, more compact than spelling out current-vs-required size as prose. When both dimensions are short at once, only one indicator is shown at a time rather than trying to fit both into a space too small for either individually (which would just recreate the truncation/overlap problem this screen exists to avoid): whichever dimension is proportionally further below its own minimum is shown, ties favoring width; resizing enough to clear that dimension surfaces the other one's indicator (if it's still short) on the next frame, walking the user through both one at a time rather than never showing anything usable in the both-short case.

No key input is processed against whatever view/overlay is underneath while this screen is showing (an overlay open underneath it stays open, whatever file was displayed stays displayed) — resizing back above both thresholds resumes the previously-active view exactly as it was, with nothing reset or changed by having passed through the too-small screen. This means quitting (`q`) is also unreachable while the terminal is too small; the process can still be terminated externally (e.g. the multiplexer/terminal's own kill/close) the same as at any other time. Because this screen must remain legible even far below its own stated minimum (e.g. a terminal resized down to a handful of columns or rows), it addresses individual cells directly rather than relying on any row- or column-wide helper that assumes the minimum it's itself guarding.

| Tab / Down | jump to file | move browser selection to the next visible match, in display order (wraps) |
| Shift-Tab / Up | jump to file | move browser selection to the previous visible match (wraps) |
| Return | jump to file | leave jump mode, browser selection stays where it is |
| Escape | jump to file | leave jump mode, restore browser selection/scroll to what they were before `/` |
| Up / Down | open-files list | move selection one entry, wraps at both ends, turns the page automatically at a page boundary |
| Page Up / Page Down | open-files list | turn a full page (10 entries), landing on the new page's first entry (clamped at the first/last page, no wraparound) |
| `0`-`9` | open-files list | select and display the entry at that position on the current page, close overlay (no-op past the current page's last row) |
| Shift-Up / Shift-Down | open-files list | move selected entry toward top/bottom of the list one position (no wraparound), page follows the moved entry |
| Shift-Page-Up / Shift-Page-Down | open-files list | move selected entry up to a full page's worth of positions (10) toward top/bottom in one keypress (no wraparound; stops early at a list end), page follows the moved entry |
| Return | open-files list | display selected entry, close overlay |
| `x` | open-files list | remove selected entry from the list |
| Escape | open-files list | close overlay, return to preview unchanged |
| (typing, including space) | content search | append to query, rescans in the background, resets disclosure to expanded-by-default |
| Backspace | content search | remove last query character, rescans, resets disclosure to expanded-by-default |
| Up / Down | content search | next/previous row — file or hit — in the flattened list (wraps) |
| Page Up / Page Down | content search | move the selection up/down by the visible row list's own height (clamped at the first/last row, not wrapping) |
| Tab | content search | move selection to the next file's own row, skipping over its hit rows (wraps) |
| Shift-Tab | content search | move selection to the previous file's own row (wraps) |
| Left | content search | collapse the selected row's file, hiding its hit rows |
| Right | content search | expand the selected file row if it's collapsed |
| Return | content search | open the selected row's file, jump to its line, leave the overlay open |
| Ctrl+R | content search | toggle substring/regex matching mode, rescans |
| Ctrl+U | content search | clear the query and results |
| Escape | content search | leave the overlay, returning to the primary preview view — query, results, selection, mode, and disclosure state are all preserved, not discarded |

Ctrl+U is the universal "clear this field" key for every free-text or numeric-entry prompt in the app (goto-line prompt, in-file find prompt, quick open, jump to file, content search): it clears the entire query back to empty in one keystroke, wherever Backspace would otherwise take repeated presses, and otherwise behaves exactly as if the query had just been backspaced down to nothing (recomputing matches/results and resetting match-selection and scroll the same way) — it never closes the prompt/overlay itself, only the query within it.

Escape is the universal "get me out of here" key for every overlay listed above, and the sole one: it closes whatever overlay is currently active, returning to the primary preview view (browse, quick open, and content search are mutually exclusive, §5.1, so none of them return to one another). Escape otherwise has **no effect** when no overlay is active (i.e. when the primary preview view itself is on screen) — it deliberately does not quit, so a reflexive Escape press can't discard the session's open-files state; `q` is the only way to quit. Its sole exception there is clearing an active in-file find (§2.4), a deliberately narrow "way out" for a state that would otherwise persist indefinitely; that still isn't a general-purpose back-out action — Escape stays inert with no active find. `b`, the key that opens the browser (§7), is not a toggle on its own overlay — once the browser is open, `b` has no effect, so Escape is the only way to close it (this keeps Escape the single, consistent close key across every overlay). Quick open is likewise not a toggle on `o` — it's a live text filter, and `o` is far too common a letter to double as a close key without breaking ordinary typing — so Escape is the only way to close it. Content search is the one overlay where Escape does not reset the overlay's own state (§9.2) — it only leaves the screen; the state itself persists until the user explicitly clears the query.

## 8. Explicitly out of scope for parity

- Mouse support was deliberately removed from the prototype (terminal multiplexer interception made it unreliable) and is **not required**. If an implementation wants to add it back for environments where it works, it must not be the only way to perform any action — full keyboard parity per §7 is required regardless.
- Exact color choices, exact spinner glyph set, and exact numeric tuning constants (byte cap, pane width cap, badge delay, spinner fps, min/max browser-pane width) are not required to match the prototype's literal values — they're implementation-tunable. What's required is the *behavior* those constants produce (bounded, sane, non-flashing, non-jarring), not the specific numbers.

## 9. Content search

Content search is a separate overlay from quick open (§4.2): where quick open matches *paths* by substring/glob and never reads a file's content, content search matches a plain string against each candidate file's *content* and lists the files that contain it. It has its own trigger key (`s`) rather than overloading `/`, `o`, or quick open's finder, and is an independent overlay with its own matching rule, distinct from both quick open and the browser's jump-to-file typing mode (§4.3).

### 9.1 Triggering and background scanning

- Entry point: `s` from the primary preview view (§2.1, including its empty state). Browse, quick open, and content search are mutually exclusive (§5.1): `s` has no effect from within the browser or quick open overlays, so reaching content search from either of those requires closing back to the primary preview view first.
- The candidate set is every non-directory entry in the background full-tree index (§4.1) — the same index quick open searches, so content search automatically honors the same `.gitignore`/`.dirtreeignore` exclusions (§3.2) and reflects the same live-refresh-triggered rebuilds (§6.1). A query typed before the index has finished building is held pending until it completes (rendered as `indexing…`), the same way quick open defers to an unfinished index (§4.2).
- Each candidate file is streamed line by line rather than read up to a byte cap: unlike preview loading (§2.1), which intentionally caps how much of a file it reads, content search has no size limit, so a match anywhere in a file is found regardless of the file's size. The leading bytes of the file are still checked for a NUL byte the same way §2.2 detects a binary open, and a file that fails that check is treated as binary and never matched — content search still never reports a match inside content it wouldn't be able to preview anyway. Because there's no size cap, a single candidate could otherwise scan indefinitely, so each candidate's scan is instead bounded by a per-file timeout: a file whose scan doesn't finish in time is cut short, keeping whatever matching lines were found before the cutoff. A file that hits this timeout, or that fails to open or read partway through (e.g. permission denied, or removed mid-scan), is still included in the results — with any hits found so far — rather than being silently dropped; the problem is shown inline on that file's row (§9.2) instead. Scanning candidates runs with bounded concurrency (multiple files at once, up to a fixed limit) rather than one at a time, so one file's per-file timeout doesn't serialize in front of every other candidate.
- Matching has two modes, toggled by the user (§9.2): **substring mode** (the default) is a case-insensitive plain-text substring match, checked line by line against the capped read; **regex mode** compiles the query as a case-insensitive regular expression and matches it line by line the same way. Content search has no glob-wildcard mode — the wildcard-vs-substring switch quick open uses (§4.1) is specific to path matching and is unrelated to content search's substring-vs-regex mode.
- In regex mode, an invalid pattern (fails to compile) is reported inline as an error in the results area and never triggers a scan — the same "don't run work you already know is wrong" discipline as the empty-query case below, just for a different reason.
- A file may match on more than one line; every matching line is kept (in source order) as that file's hits, and all of them are exposed in the result list (§9.2) — this is a full per-line results list, not just a first-example lookup.
- Scanning always runs in a background goroutine (mirroring §4.1's non-blocking discipline), never on the UI/input thread: each keystroke that changes the query or mode cancels any still-running scan for the previous query/mode and starts a new one over the full candidate set, so a scan — however slow, e.g. a broad regex over a large tree — never blocks keystrokes, only its own result arrives late. Only the most recently started scan's result is ever applied; a result from a canceled/superseded scan is discarded.
- An empty query performs no scan and shows no results — this is deliberately different from quick open's "empty query matches everything" (§4.1): quick open's empty-query match is a free lookup against an already-built in-memory path list, while scanning every candidate file's content on an empty query would mean reading the entire tree for no useful result.
- While a scan for the current query is in flight, or the background index itself isn't done yet, the results area shows a `searching…`/`indexing…` placeholder instead of "no matches" — the same "don't claim zero results before you've actually looked" rule §5.2 uses for quick open's own delayed-loading state. Once a scan has been running long enough to be perceptible, `searching…` gains an animated spinner glyph, the same threshold-suppressed feedback the background-index badge uses (§5.2) — nothing flashes for a scan that finishes in a blink, but a genuinely slow one (large tree, broad regex) gets visible, non-jarring feedback that it's still working rather than looking stuck.

### 9.2 Mode behavior

- The screen is fully replaced by a header row (bold, all-caps `SEARCH` mode label, plus the keybinding legend), a dedicated query-input row directly below it showing the query as typed (e.g. `> needle`), and below that a two-level list view: one **file row** per matching file (its root-relative, slash-delimited path plus its total hit count), each disclosing its own **hit rows** underneath — one per matching line in that file, indented past the file row's own path text (not merely aligned with it) so a hit row reads as visually nested under its file rather than as a sibling, showing the 1-based line number and that line's (trimmed) text. Every file row starts expanded (all of its hits visible) as soon as results arrive; nothing needs to be manually opened to see them. The query lives in its own row, separate from the legend, so a long query and a long legend never have to compete for the same line, and is rendered with a background distinct from the plain-background results list below it, so the "you're typing here" row reads at a glance. While regex mode (below) is on, the query row's prompt is prefixed `[regex] ` (e.g. `[regex] > needle`) rather than plain `> ` — this lives on the query row rather than the header's mode label so it doesn't compete for header width with the keybinding legend, and rather than the legend's own `ctrl+r` entry so it stays visible even when narrow-terminal drop rules (§5.2) have dropped that entry. Once results exist for the current query (including a zero-match result — this is not gated on there being at least one hit), the query row's right side additionally shows a `N hits across N files` summary, right-aligned with at least one space of separation from the query text on its left, the same left-text-plus-right-aligned-content composition the header/title bar and file title bar (§5.2) already use elsewhere, just without an accompanying keybinding legend on this particular row. Both counts total only files that actually contributed at least one hit — a file present in the results solely because of a scan issue (§9.1) with zero hits counts toward neither total — and each noun is singular (`1 hit`/`1 file`) exactly at 1, plural otherwise. If the query text plus the summary can't both fit the row's width, the summary is dropped entirely rather than truncated (the query itself is never truncated to make room, since losing sight of what was typed would be worse).
- A file row whose path is already in the open-files list (§2.2) — because it was opened from here, from the browser, from quick open, or is simply still open from earlier in the session — shows a lasting "●" open indicator alongside its disclosure marker, reflecting the open-files list's live state rather than only this overlay's own open actions. This indicator is file-row-only; it is never repeated on the hit rows underneath, since "open" is a fact about the file, not about any one line in it.
- Each file row shows a disclosure indicator (expanded vs. collapsed) reflecting its own independent expand/collapse state. **Left** collapses the file the current selection belongs to (hiding its hit rows and moving the selection to that file's own row, if it wasn't already there); **Right** expands the currently-selected file row if it's collapsed. Collapsing/expanding one file never affects any other file's disclosure state.
- A query string starts empty and accumulates/removes characters as the user types/backspaces, shown on its own row (above). Because a content-search query is literal text rather than a path fragment, the space bar always types a literal space into the query — unlike the finder overlays, no printable key is overloaded to double as an action key; every action below is on a non-printable key instead.
- **Ctrl+R** toggles between substring mode (default) and regex mode (§9.1), re-running the scan for the current query under the new mode. The active mode is shown in the header title.
- A `selected` index into the current flattened row list (file rows plus, for expanded files, their hit rows), with wraparound cycling: advance forward (Down) or backward (Up). Collapsing a file removes its hit rows from this list; expanding it reinserts them, always in source order. **Page Up / Page Down** move the selection by a full visible-row-list-height jump instead of one row at a time, clamped at the first/last row rather than wrapping (the same convention quick open's, §4.2, and the browser's, §3.4, own Page Up/Down use). **Tab / Shift-Tab** move the selection directly to the next/previous file's own row — skipping over any hit rows in between, and wrapping at both ends — a coarser jump than Up/Down's one-row-at-a-time walk, useful once a file's hits have already been reviewed and the next thing to look at is a different file entirely.
- **Return**, if there is at least one row: open the selected row's file into the open-files list per §2.2's open semantics (reusing an existing open-files entry if the path is already open), then jump the preview's scroll to that row's line — the selected hit's line if a hit row is selected, otherwise the file's first (lowest-line-number) hit if a file row is selected — the same jump-to-line behavior goto-line uses (§2.1). Unlike quick open/jump to file, opening a result here does **not** close the overlay — the primary preview view updates underneath it, but content search stays on screen, so several hits can be opened in a row without re-entering the search each time; Escape (below) is what leaves the overlay once you're done. A "failed" result (read error or binary — e.g. the file changed or was removed between scanning and opening) leaves the overlay open with the message shown inline instead, per §2.2's open-failure signaling — the same outcome as a successful open, just with a message instead of a moved preview. On success, the opened file's row (its file row, even if a hit row was the one selected) also gets a brief style flash — distinct from both the cursor's `styleSelected` highlight and the lasting "●" open indicator above — as one-shot confirmation that this particular Return actually opened something, fading back to normal after a short, fixed duration (400ms in the prototype) rather than being cleared by any specific follow-up action. As with quick open (§4.2), a successful open also reveals the path in the browser (every intermediate ancestor expanded, browser selection moved to it), so opening the browser afterward shows where that file lives without further navigation.
- **Ctrl+U**: clear the query and results back to empty — the explicit way to reset a search, since (per Escape below) leaving the overlay no longer does this itself. The regex-mode toggle is left as-is; it's a standing preference, not part of the query being cleared.
- A file row whose scan (§9.1) hit a problem — a read error partway through, or the per-file scan timeout — shows that problem appended after its match count (or in place of a match count, if no hits were found before the problem), rendered in the same contrasting error style the invalid-regex message above uses. This persists until the row is replaced by the query's next rescan, unlike the transient red open-failure flash (§2.2, §5.3): that one is about a failed *open* action on a row the user selected, this one is about the *scan* itself not completing cleanly, and the two can appear on the same row for different reasons at different times.
- **Backspace**: remove the last character of the query, cancel any in-flight scan for the old query, and start a new one for the shortened query (or, if the query is now empty, show no results without scanning). Also resets every file's disclosure state back to expanded-by-default for the new result set.
- **Escape**: leave the overlay, returning to whichever screen it was opened from. Unlike quick open/jump to file, this does **not** discard anything — the query, results, in-flight scan, selection, mode, and each file's disclosure state are left exactly as they were, so reopening the overlay (`s`) resumes right where it was left. The query and results are only ever reset by the user explicitly clearing them (Ctrl+U, backspacing the query to empty, or typing a new one).
- Typing any other printable character, including space, appends it to the query, cancels any in-flight scan for the old query, starts a new one, and (like Backspace) resets disclosure state to expanded-by-default for the new result set.
