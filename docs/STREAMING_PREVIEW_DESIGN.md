# Streaming preview view: design proposal

This is a design proposal, not a spec — nothing here is decided or scheduled, and none of it is implemented. It exists to work through the feasibility of removing the preview pane's fixed read cap (`preview.DefaultByteCap`, `specs/SPEC.md` §2.1) while keeping goto-line fast, before committing to an approach. If and when this is actually built, its real behavior belongs in `specs/SPEC.md` (with acceptance criteria added to `specs/TESTING.md`), the same discipline `docs/ANIMATION_IDEAS.md` follows for its own not-yet-built ideas — this document should be treated the same way that one is.

## 1. Problem statement

Today's preview pipeline (`internal/preview/read.go`, `internal/openfiles/openfiles.go`, `internal/ui/views/preview.go`) is fully eager: `preview.Load` reads up to 1MB once at open time, decodes it, runs Chroma highlighting over the whole thing in one call, and `openfiles.Entry` keeps the full `Lines`/`Segs` slices resident for the life of the entry. `ensureWrapped` rebuilds a `Rows`/`FirstRow` map over *every* source line whenever the viewport width changes, and goto-line is an O(1) lookup into that map. None of this scales past the byte cap by design — the cap exists precisely to bound memory/latency on huge files (§2.1's own comment).

The ask: read a file of any length, keep goto-line working, and build a line-offset mapping asynchronously with a spinner-style indicator. That mapping turns out to be unconditional infrastructure, not something conditionally built only for some files: every open file gets one, in the background, regardless of size or which highlighting tier (§2) it falls into, since goto-line's correctness depends on it either way (§4 covers why). The spinner is proposed to live in the file title bar's legend (`internal/ui/views/preview.go`'s `fileLegend`) rather than the corner badge, since this is per-file state, not global indexing state.

## 2. Two-tier strategy

Rather than one uniform "always stream everything" mechanism, the design splits on a single highlighting size ceiling (§5 below) into two tiers. This isn't just a simplification — it's forced by a hard constraint in Chroma's public API (§6): once a file is small enough to highlight, keeping its decoded content and computed segments resident is both safe and the simplest way to get correct, stable highlighting; once it's past that ceiling, correct highlighting isn't obtainable without holding the whole thing anyway, so the design instead drops highlighting and goes fully windowed.

**Tier A — at or under the highlighting ceiling.** Behaves like today's model, just made non-blocking: read, decode, and highlight the whole file once, in a background goroutine kicked off at open time instead of synchronously inside `openfiles.List.Open`. Content and segments are kept fully resident for the entry's lifetime exactly as now. The only user-visible change is that opening a file at or near the ceiling no longer blocks input while it loads — the entry appears immediately with a "building…" state (§7) and lights up once the background pass finishes, typically fast enough that the indicator never crosses the perceptibility threshold at all, the same "don't flash chrome for instant work" rule the indexing badge already follows (§5.2).

**Tier B — over the ceiling.** No highlighting; content is rendered as plain text (a single `CategoryText` segment per line, the same fallback `preview.Load` already uses when no lexer matches). Nothing about the file is read wholesale — a background pass streams through it once to build a byte-offset line index (§4), and the preview pane reads only the lines actually needed for the current viewport (plus a small scroll margin), seeking via that offset table. This is the tier that actually delivers "read to any length": memory use for a multi-GB file stays proportional to the viewport, not the file.

A file's tier is decided once, at open time, from its size (a `Stat` call, no read required) — there's no promotion from B to A mid-session, and no user-facing toggle proposed here (see open questions, §11, for whether that's wanted).

## 3. What's shared across both tiers

Both tiers need the same background worker shape: a per-entry goroutine, started the moment `openfiles.List.Open` decides to create an entry (after the existing failed-read/binary check, which still happens synchronously and fast via `readCapped`'s existing first-chunk peek — see §9 for how the binary check adapts once there's no cap), that streams the file once and publishes progress into a mutex-guarded snapshot struct the UI polls — the exact concurrency shape `internal/index.Index` already uses for the full-tree index (§4.1 of the spec), chosen for the same reason: no shared mutable state between the UI goroutine and the background one, so no locking is needed on the hot path, only on the snapshot's own accessor methods.

```go
// internal/preview/stream.go (sketch, not final)
type StreamIndex struct {
    mu        sync.RWMutex
    offsets   []int64       // byte offset of the start of each line seen so far
    segs      [][]Segment   // Tier A only: per-line highlight segments, same shape as today's Entry.Segs
    lineCount int           // len(offsets); read under mu, or via atomic if profiling says the mutex matters
    done      bool
    startTime time.Time
    tier      Tier          // TierHighlighted or TierPlainText, decided at Start
}

func StartStream(path string, tier Tier) *StreamIndex
func (s *StreamIndex) Snapshot() (offsets []int64, segs [][]Segment, lineCount int, done bool)
func (s *StreamIndex) Elapsed() time.Duration
```

This is deliberately the same shape as `index.Index`'s `Start`/`Snapshot`/`Elapsed` — same rationale, same review-familiarity, no new concurrency pattern to learn.

## 4. The line-offset index

Regardless of tier, a single background pass records the byte offset of every line's start as it goes (a `bufio.Reader.ReadString('\n')` loop, the same streaming shape `internal/search`'s `scanFile` already uses for content search — §9.1 of the spec streams every candidate file line by line rather than capping it, so this isn't a new pattern in the codebase, just a new caller of it). This is cheap: an `[]int64` of offsets is a small fraction of the file's own size (roughly 8 bytes per line, so a file with a million lines costs ~8MB of index regardless of how large the lines themselves are), and it's what makes goto-line, the gutter width, and windowed scrolling all work without holding the file's content.

**Goto-line while the index is incomplete.** Revised from an earlier queueing proposal: goto-line is disabled outright until the background pass for the *displayed* entry finishes completely, not just up to the requested line. Pressing `g` while that pass is still running doesn't open the goto-line prompt at all — it instead flashes the file title bar red and shows a brief inline message (e.g. "still indexing, try again shortly"), reusing the exact red-flash-plus-inline-message convention `specs/SPEC.md` §2.2/§5.2 already uses for a failed file open (the flash decays after its own fixed duration, the message persists until overwritten). This is a deliberate rejection, not a silent wait: the file-legend spinner (§7) already tells the user the index isn't ready before they ever press `g`, so the red flash specifically covers the case where they press it anyway — the same "this action failed, and here's why, right where you took it" pattern the rest of the app already uses for failure, rather than a new queued-and-eventually-honored affordance. This is simpler to reason about and implement than queueing, at the cost of goto-line being unavailable for the (typically brief, especially in Tier A) duration of the *whole* pass, rather than resolving progressively line by line as the queueing approach would have — a real cost on a genuinely huge Tier B file (goto-line stays unavailable for the entire scan, even to reach an early line whose offset was resolved almost immediately), but one deliberately accepted here in exchange for the simpler implementation and the simpler, single "ready or not" mental model, given how rarely a file that large is actually opened in practice.

**Gutter width** (`canvas.GutterWidth`, sized off total line count) has no exact answer until the pass finishes for Tier B. Render it against the *best current lower bound* (`lineCount` from the snapshot) while the pass is running, the same "recompute fresh from whatever's currently known" discipline the rest of the app already applies to layout (§6.2), floored at a minimum width of 4 digits regardless of how few lines have been indexed so far — most files exceed 1,000 lines eventually, so a 4-digit floor means the large majority of Tier B files never visibly resize their gutter at all; only files that end up past 9,999 lines still show the (now much rarer) grow-then-snap wobble once the pass completes.

## 5. The highlighting size ceiling

Tier A/B's dividing line is a single size threshold, checked via `Stat` before the background worker starts. Default: **25MB**, picked as a reasonable starting point rather than derived from measurement — large enough that the overwhelming majority of source files (even generated ones) stay in Tier A and keep their syntax color, small enough to bound Chroma's `[]rune` blow-up (§6) to roughly 100MB peak in the worst case. Like `search.go`'s `perFileTimeout`/`maxConcurrentScans`, this is a `var`, not a `const`, specifically so it can be tuned later against real data (the same way those two were, per their own doc comments) without needing a code change to experiment, and so tests can exercise both tiers without needing to generate a real 25MB fixture. No user-facing override to force Tier A behavior past this size is proposed — once a file lands in Tier B, it never gets syntax color in this design (§11).

This ceiling is doing two independent jobs at once, both explored in this design conversation:

- **Fidelity**: Chroma's stateful lexers (block comments, multi-line strings) must be tokenized in order from the start to be correct at any offset — there's no reliable way to jump into the middle of a large file and highlight just the visible window without either re-running the whole prefix or accepting occasional wrong categorization at the jump point. Tier A sidesteps this by always running the pass to completion in the background; Tier B sidesteps it by not attempting highlighting at all past the ceiling, rather than shipping a heuristic that's sometimes wrong.
- **Memory**: see §6 — Chroma's tokenizer needs the whole input resident as a `[]rune` to run at all, and (per §6's finding) there is no supported way to chunk that input and carry lexer state across chunk boundaries. The ceiling is the only available deterministic bound on that cost, since chunked resumption turned out not to be available through Chroma's public API.

## 6. Why chunked re-lexing isn't available (and why the ceiling has to do this work instead)

Chroma's `Lexer.Tokenise(options *TokeniseOptions, text string) (Iterator, error)` takes the entire input as a Go `string` and, in `RegexLexer.Tokenise` (`regexp.go`), immediately converts it to `[]rune` (`Text: []rune(text)`) before returning an iterator — up to 4 bytes per rune, so a large ASCII-heavy file can balloon to several times its own size in memory for the duration of the pass. The tokenizing work itself is lazily pulled (`Iterator` is `func() Token`, computed on demand as the caller ranges over it), which would make it straightforward to spread the CPU cost across a background loop — but the `[]rune` conversion happens up front, in one allocation, regardless of how the resulting tokens are consumed afterward.

The natural fix would be to tokenize in bounded chunks and carry the lexer's state (which regex-state it's in — inside a string, a block comment, etc.) into the next chunk's starting options. This turns out not to be supported: `TokeniseOptions.State` only lets a caller *seed* a fresh single-level starting state (`Stack: []string{options.State}` in `regexp.go` — a stack of depth exactly one), and `Tokenise` returns only the bare `Iterator` closure, with no way to read back what state (or state stack) the lexer ended a chunk in. So even accepting the "single-level stack only" approximation isn't possible — there's no accessor to retrieve the ending state at all through the public API. Confirmed by reading `chroma/v2@v2.27.0`'s `lexer.go`, `regexp.go`, and `iterator.go` directly rather than assumed from memory.

Practical consequence: for a file under the ceiling, the one-time `[]rune` cost is accepted (as it already is today, synchronously, at open time — this design just moves it to a background goroutine, it doesn't add a new cost). For a file over the ceiling, highlighting is skipped entirely rather than attempting any partial or approximate version of it — there is no middle ground available given the library's API.

## 7. UX: the file-legend spinner

`internal/ui/views/preview.go`'s `fileLegend` (`[/] find`, `[g] goto line`, `[c] copy mode`) gets a fourth state: while the *displayed* entry's background stream/highlight pass is still running and has crossed a perceptibility threshold, the `[g] goto line` entry is replaced with a "building…" indicator carrying the same spinner glyph the indexing badge uses (`internal/spinner.Frame`, same fixed frame set and fps) — reusing `spinner.ShouldShow`'s threshold-suppression and (for Tier A, where the pass is expected to finish almost immediately for most files) the same minimum-display-duration floor, so a fast pass never flashes chrome for genuinely instant work, matching §5.3's existing animation principles rather than inventing new ones. This is deliberately anchored to the file title bar, not the corner badge — it's per-open-file state, unrelated to the full-tree index the corner badge already reports on, and the two can legitimately be visible at once (opening a huge file while the tree index is still building).

Once the pass finishes, the entry reverts to the normal `[g] goto line` legend. Unlike the rest of the app's animations, this legend state *does* gate one specific action: goto-line (§4) is unavailable for as long as it's showing, by design — pressing `g` while it's up flashes the file title bar red and explains why, rather than opening the prompt. This is a narrow, deliberate exception to §5.3's "never block the UI" principle, which is about an animation never gating input on reaching a particular frame or timer of its own — goto-line isn't blocked on the spinner's timing, it's blocked on data (the line-offset index) that genuinely doesn't exist yet, and the spinner is simply the advance notice for that fact. Scrolling, in-file find (Tier A), copy mode, and every other key stay fully live throughout.

For Tier B specifically, a jump ahead of where the pass has reached can still show *plain-text* content immediately once the offset is known (content availability lags behind highlighting availability in Tier A too, but in Tier B there's no highlighting to lag) — for Tier A, a plausible refinement is to show the plain-text fallback for not-yet-highlighted lines and let them "light up" once the pass's `segs` catches up to that point, which is informative (visibly communicates ongoing background work) rather than decorative, consistent with §5.3, though this adds a second render path (plain vs. highlighted) that a simpler first cut could defer — see the phased plan (§10).

## 8. Windowed content for Tier B

Tier B never holds decoded line content for the whole file. `drawContent`'s render loop (`internal/ui/views/preview.go`) currently indexes directly into `e.Rows`, built once by `ensureWrapped` over the whole `e.Segs`. For Tier B this needs to become: given the current scroll position (now a *line number*, not a display-row index into a precomputed slice — see below), seek to that line's offset, read forward far enough to fill the viewport plus a small margin, wrap only those lines, and discard the result once scrolled away. This is a real change to the preview view's scroll model, not just the data layer underneath it — worth calling out as the largest single implementation item in this design, separate from the background-worker plumbing.

Wrapping (`preview.BuildDisplayRows`) doesn't need to change at all for this — it already operates on whatever slice of `[]Segment` it's given; Tier B just calls it with a small windowed slice instead of the whole file's.

## 9. In-file find over Tier B files

`performFind` (`internal/ui/views/preview.go`) is currently a synchronous linear scan of `e.Lines` — fine when the whole file is resident, not fine once it isn't. Over a Tier B file, `/` needs the same treatment `internal/search` already gives full-tree content search: a background, cancelable, streamed scan (reusing `search.scanFile`'s shape directly, or extracting its line-streaming loop for both callers to share), with its own perceptibility-threshold spinner in the find status area rather than blocking the keystroke. This is scoped to Tier B only — Tier A's `e.Lines` is fully resident, so today's synchronous scan stays correct and fast there; no reason to change it.

## 10. Memory and GC impact, revised for this project's actual deployment target

The first pass of this exploration flagged GC-driven hitches as a risk and reasoned about it partly in terms of small (1-2 vCPU) per-app containers — the wrong target for this project. Confirmed deployment is dev workstations and bare-metal servers (Fedora bootc), not one-container-per-app scheduling, so the sharpest version of that risk (a background mark phase competing with the render goroutine for a scheduler with almost no spare capacity) is less likely to bite in practice — these are generally multi-core machines with headroom. That said, two things keep this worth bounding rather than ignoring: a dev workstation can still be under real memory/CPU pressure from everything else running on it (browsers, IDEs, other services), and a shared bare-metal server may be running other workloads dirtree has no visibility into — so "bound the worst case" is still worth doing, just not with the urgency of the container framing.

Go's GC stop-the-world pauses (mark start/mark termination) are sub-millisecond regardless of heap size; the actual cost of a large one-time allocation is the concurrent mark phase's CPU competition with other goroutines (up to 25% of `GOMAXPROCS` reserved for background mark workers, plus possible mark-assist debt charged to whichever goroutine is allocating fastest — ideally the background stream worker, not the render goroutine, since the render loop itself allocates very little per frame). On the confirmed target hardware this is a real but modest risk, not a headline concern — still worth the following, low-cost mitigations, none of which require process-wide GC tuning:

- The size ceiling (§5) is the primary, deterministic bound: above it, there's no `[]rune` blow-up at all, since highlighting is skipped.
- Serialize background streaming/highlighting passes with a small semaphore (mirroring `search.go`'s `maxConcurrentScans`) so opening several large files back-to-back doesn't stack simultaneous spikes — cheap insurance, not a response to a specifically severe risk on this target.
- Let the transient decode buffer and Chroma's `[]rune` copy go out of scope as soon as that file's pass finishes, rather than holding raw text alongside computed segments any longer than needed.
- Not recommending `debug.SetGCPercent`/`SetMemoryLimit` tuning or proactive `debug.FreeOSMemory()` — blunt, process-wide knobs for what's really a one-file, one-time event, and `FreeOSMemory` forces its own STW cycle. If real profiling on the actual target hardware later shows this mattering, revisit then rather than pre-optimizing for a container scenario that doesn't apply here.

## 11. Open questions

- **Tier B and in-file find**: does it get its own size/time ceiling independent of the highlighting ceiling (a find could still be slow on a many-GB file even though reading/scrolling stays cheap), mirroring `search.go`'s `perFileTimeout`?
- **Tier A "lights up" animation** (§7): worth the second render path, or is a straightforward "legend spinner, then full highlighted content all at once" a good enough first cut?
- **Reload behavior** (`openfiles.List.Reload`, §6.1a): a live-refresh-triggered reload of a Tier B file currently means re-reading up to the cap; under this design it means restarting the whole background stream. Is that acceptable, or does it need its own debouncing/coalescing beyond what `watch.Watcher`'s existing debounce already provides?
- **Real timing numbers for the whole-file-block tradeoff** (§4): the whole-file block decision was made accepting some latency on genuinely large files as an acceptable tradeoff for now, on the assumption that files large enough to make the background pass noticeably slow are rare in practice. That assumption is currently unverified — actual wall-clock numbers for the line-offset (and, in Tier A, highlighting) pass across a range of real file sizes (mirroring how `search.go`'s `perFileTimeout`/`maxConcurrentScans` were tuned against real measurements rather than guessed) would confirm whether it holds, and would also inform the ceiling value (§5) and the in-file find ceiling above. Explicitly out of scope for this design/implementation pass — a follow-up measurement task, not a blocker to landing the phased plan (§13).

Two questions from the first draft are decided rather than open: the ceiling value defaults to 25MB (§5), tuned later against real data instead of upfront measurement; and there is no user override to force highlighting past the ceiling (§5) — once a file is in Tier B, it never gets syntax color in this design.

## 12. Testing implications

Per `CLAUDE.md`'s testing discipline, the pure-logic pieces need automated coverage grouped against `specs/TESTING.md` the same way existing preview tests are: `StreamIndex`'s offset-building logic, goto-line's block/allow decision (a pure function of whether the displayed entry's stream pass is done), the tier decision itself (a pure function of file size and the ceiling), and the file-legend spinner's show/hide decision (a pure function of `(elapsed, done, threshold)`, the same shape `spinner.BadgeDecision` already is and already unit-tested without a real terminal or real elapsed time). The actual GC/scheduling behavior under load, and real large-file scrolling smoothness, are not unit-testable and would need the same manual-verification treatment `internal/ui` already gets — in a real terminal (tmux/Zellij), against fixtures larger than `examples/`'s current synthetic files, ideally with `GODEBUG=gctrace=1` to correlate any perceived lag with actual GC activity rather than guessing.

## 13. Phased implementation plan

1. Background `StreamIndex` worker building the byte-offset line index only, for every open file regardless of size; goto-line is blocked (file title bar flashes red, with an explanatory message, if invoked early) until that entry's pass finishes; reading/highlighting/wrapping stay exactly as they are today (still capped) — this alone delivers "goto-line survives being async" and the file-legend spinner UX, independent of the harder Tier B work.
2. Fold the ceiling decision and Tier A/B split in: Tier A keeps today's full-file highlighting, just moved to the same background worker and made non-blocking; Tier B drops the cap for reading but renders plain text only, with windowed on-demand reads replacing `ensureWrapped`'s whole-file wrap for that tier.
3. Async in-file find for Tier B, reusing `internal/search`'s streaming/cancellation pattern.
4. (Optional, pending §11) Tier A's "lights up" progressive-highlighting animation, if the plain first cut in step 2 turns out to feel incomplete in practice.

Each step should update `specs/SPEC.md` (§2.1, §5.2, §5.3) and `specs/TESTING.md` in the same change that lands it, per `CLAUDE.md`'s "don't let code and spec diverge silently" rule — this document is the pre-implementation exploration, not a substitute for that.
